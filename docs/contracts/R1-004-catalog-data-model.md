# R1-004 — модель данных каталога

**Статус: FROZEN. Версия: 1.0.0.** Утверждено владельцем 2026-10-24 (Asia/Vladivostok) на исходном SHA `8ae4dd8cfd15e3722d97259818b238924851c963`. Основание: R1-004A, CAT-02…CAT-06, SRC-03…SRC-05/SRC-07, решения #1, #2, #6, #24…#26, #32…#34, #49, #55…#58 и #60. R1-002 1.0.0 остаётся неизменным. Утверждение разрешает реализацию R1-004B, но не production migration/deployment.

## 1. Границы модели

Таблицы R1-004: `Brand`, `Category`, `AttributeDefinition`, `CatalogProduct`, `CatalogProductRevision`, `ProductAttributeValue`, `ProductMedia`, `ProductDocumentVersion`, `ProductRelation`. Единственная дополнительная сущность относительно исходного перечня — `CatalogProductRevision`; она обязательна, чтобы хранить неизменяемые опубликованные редакции отдельно от изменяемых данных редактора. Для привязки атрибута к точной категории используется `AttributeDefinition.categoryId`; отдельная таблица связи не нужна. Поля каждой таблицы и machine-readable ограничения перечислены в [R1-004-catalog-data-model.json](R1-004-catalog-data-model.json).

Не входят `Supplier`, `SupplierOffer`, `IngestionRun`, `ImportJob`, `PricingRule`, склад, заказ и производственные сущности. Каталог не создаёт файловые байты и не выдает их. Из файловой модели R1-002 используется только FK на конкретный `FileVersion`.

## 2. Общие правила хранения

- PostgreSQL — единственный источник истины. Prisma 7.10.1 и Prisma Migrate остаются единственным ORM/migration owner по ADR-001. Все FK — `ON DELETE/UPDATE RESTRICT`; API не удаляет справочники, продукты, редакции и связи физически.
- PK — UUIDv4 CSPRNG; даты — UTC `timestamptz(6)`; счётчики редакций и `version` — положительный int32. Мутации принимают `expectedVersion`; конфликт возвращает 409 `VERSION_CONFLICT` без частичных изменений.
- Все пользовательские строки ограничены по длине и очищаются по внешним пробелам; описание — plain text, не HTML. Неизвестные поля DTO отклоняются. Slug — уникальный ASCII lower-case `^[a-z0-9]+(?:-[a-z0-9]+)*$`, вводится редактором, без неявной транслитерации. Опубликованный product slug не меняется; slug не переиспользуется и после архивации.
- Справочные состояния: `ACTIVE | ARCHIVED`; физического удаления нет. Архив категории блокируется, пока у неархивного продукта её содержит текущий draft, pending или published pointer, либо пока у неё есть активный дочерний узел; старые non-current returned/rejected/superseded revisions не блокируют архив. Архив бренда блокируется, пока его использует identity неархивного продукта. Архивный атрибут остаётся читаемым в старых редакциях, но не выбирается для новых.
- Права и статусы проверяются только NestJS. Запись, изменение ссылки, решение о публикации и соответствующий `AuditEvent` выполняются одной PostgreSQL-транзакцией; failure Audit откатывает мутацию.

## 3. Идентичность продукта

`Brand` — торговый бренд и отдельный FK; `manufacturerName` — производитель; `originalPartNumber` — оригинальный идентификатор производителя; `modification` — модификация/исполнение. Эти поля не взаимозаменяются и не выводятся автоматически одно из другого. Бренд может быть неизвестен; если один из обязательных ключевых компонентов отсутствует, продукт не получает автоматический dedup key.

**Рекомендация владельцу OD-004A-01:** полный ключ идентичности — `(brandId, manufacturerName, originalPartNumber, modification)`. Для `manufacturerName`, `originalPartNumber` и `modification` сравнение регистрозависимое, после Unicode NFC и удаления только внешних U+0020 пробелов; внутренние пробелы, регистр, дефисы и пунктуация сохраняются. PostgreSQL выражения уникального индекса используют `COLLATE "C"`, чтобы сравнение не зависело от локали БД. `NULL` modification означает отсутствие модификации и отличается от любой непустой строки. Частичный уникальный индекс применяется только когда brand, manufacturer и original part number заданы. Дубликат отклоняется как `IDENTITY_CONFLICT`; система не объединяет карточки и не предлагает функциональный аналог.

При создании товара root tuple и начальная DRAFT snapshot создаются из одного запроса в одной транзакции. До первой успешной отправки каждая замена draft атомарно обновляет root tuple и создаёт совпадающий DRAFT snapshot; прежняя SUPERSEDED редакция сохраняет свой первоначальный snapshot. Уникальность проверяется ограничением root во время этой же транзакции, конфликт даёт `IDENTITY_CONFLICT`. Первая успешная отправка замораживает root tuple. Каждая последующая редакция копирует его без изменений; несовпадение root и revision identity отменяет транзакцию. Исправление после первой отправки требует отдельной ручной операции по утверждённому решению и не входит в R1-004B.

## 4. Динамические технические атрибуты

Одна `AttributeDefinition` относится к ровно одной категории; наследование атрибутов по дереву в предложении не включено. Вложенные категории получают собственные определения. Для чтения/изменения определений указываются `categoryId`; одинаковый `code` может повторяться в разных категориях, но уникален внутри категории. Фильтр по техническому атрибуту обязан указывать категорию, чтобы тип и единицы были однозначны.

Типы: `TEXT`, `DECIMAL`, `INTEGER`, `BOOLEAN`, `ENUM`. `TEXT` ограничен 240 Unicode characters и PostgreSQL `varchar(240)`. `unitCode`/`unitLabel` задаются для числовых измерений; конверсия единиц автоматически не выполняется. DECIMAL передаётся канонической base-10 строкой без экспоненты, не более 64 символов, без ведущего плюса/нулей, завершающих дробных нулей и отрицательного нуля; INTEGER — JSON integer в безопасном диапазоне ±9 007 199 254 740 991; промежуточное округление через binary float запрещено. `enumOptions` хранится как закрытый непустой список уникальных `{code,label}`. Запрос передаёт discriminated `valueType` и значение; сервер обязан сверить тип с загруженной `AttributeDefinition` и проверить enum code по этой записи. `ProductAttributeValue` содержит отдельную typed-колонку, nullable-колонки взаимоисключаются CHECK, а составной FK гарантирует совпадение `categoryId` и типа с определением. Приложение/DB guard валидируют уникальность enum codes, значение по типу, диапазон и применимость до записи; прямое значение не интерпретируется как HTML/SQL.

Значение хранит snapshot кода, подписи, типа, единицы и флагов поиска/фильтрации/сравнения на момент редакции товара. После появления значений семантические поля определения (code/type/unit/options) не изменяются; новая семантика оформляется новым определением. Переименование подписи влияет только на будущие редакции. Единица значения никогда не меняется без новой редакции товара.

## 5. Публикация и редакции

`CatalogProduct` — стабильная identity/root-запись с `publicationState`, `publishedRevisionId`, `pendingRevisionId`, `currentDraftRevisionId` и OCC `version`. Все три составных pointer FK привязаны к тому же `productId`; транзакционные guards проверяют, что каждый указатель ведёт только на редакцию соответствующего состояния, а на продукт допускается не более одной ожидающей проверки редакции. `CatalogProductRevision` содержит полный snapshot публичных полей, nullable FK `brandId` и FK `categoryId` со значениями Brand/Category на момент создания, идентичность товара, typed attributes, media/document metadata и ручные relations. `sourceRevisionId` составной FK `(sourceRevisionId, productId)` не позволяет копировать основу из чужого продукта.

Каждая команда изменения draft создаёт новую неизменяемую редакцию `DRAFT` из явно указанной `baseRevisionId`. Если `currentDraftRevisionId` задан, это должен быть текущий draft. Под `FOR UPDATE` root lock транзакция временно очищает этот pointer, переводит предыдущий `DRAFT` в терминальный `SUPERSEDED`, вставляет новый `DRAFT` и устанавливает новый pointer; deferred transaction guard проверяет pointer/state согласованность на commit. Частичные unique indexes разрешают не более одного `DRAFT` и одного `PENDING_REVIEW` на root. Если текущего draft нет и pending отсутствует, основой должен быть самый новый `RETURNED`/`REJECTED` revision, созданный позже текущей опубликованной редакции; если такого нет — текущий опубликованный revision. Для ещё не опубликованного продукта используется последний `RETURNED`/`REJECTED`. Любой другой `baseRevisionId` даёт `VERSION_CONFLICT`. Поэтому тот же PATCH запускает новую линию редактирования после первой публикации и после возврата/отклонения. Пока существует pending revision, редактирование блокируется. Повтор без изменения — read-like no-op. Содержимое редакции после вставки не обновляется; разрешены только переход статуса и поля решения, защищённые триггером/сервисом и транзакцией. `createdBy/createdAt`, `sourceRevisionId`, `submittedBy/submittedAt`, `decidedBy/decidedAt`, reason и audit сохраняются. В R1-004 источник изменения — только `STAFF_MANUAL`; импортное происхождение добавляется вместе с отдельной задачей R1-006.

Статус root `DRAFT → PENDING_REVIEW → PUBLISHED → ARCHIVED` описывает первую публикацию и текущую публичную доступность. Root `pendingRevisionId` указывает единственную ожидающую редакцию; `currentDraftRevisionId` — только редактируемую `DRAFT`. Submit перемещает указатель с draft на pending; решение очищает pending. При первом возврате/отклонении root становится DRAFT, у уже опубликованного товара root остаётся PUBLISHED. Для опубликованного продукта новая draft/pending редакция не меняет root из `PUBLISHED` и не меняет `publishedRevisionId`; публичная карточка продолжает читать только старый pointer. Решение публикации атомарно переводит новую редакцию в `PUBLISHED`, перемещает published pointer, увеличивает root version и пишет аудит.

`RETURN_FOR_CHANGES` завершает submitted revision статусом `RETURNED`; редактор создаёт следующую draft-копию с `baseRevisionId` этой редакции, сохраняя комментарий reviewer. `REJECT` завершает revision статусом `REJECTED`; опубликованный pointer не меняется, но после решения новая draft-копия может быть создана из этого отклонённого revision. Повторное редактирование/submit создаёт новую revision; история решений не переписывается. `ARCHIVE` — терминальная команда из любого неархивного root-state: отменяет pending revision как `WITHDRAWN`, очищает все три current pointers, скрывает root и его публичный pointer, но не удаляет файлы, editor history или опубликованные редакции.

Публикация — отдельное действие с правом `catalog.products.publish`, reviewer, временем, revision ID и аудитом. Разделение permissions `submit` и `publish` обязательно; правило «автор не может утвердить собственный submit» исходными решениями не задано, поэтому предложено разрешать публикацию тому же сотруднику только если он независимо имеет publish permission. Это один из вопросов OD-004A-02.

## 6. Справочники и связи

- Категория — adjacency list `parentId`; `sortOrder` — nonnegative int32 с DB CHECK и таким же ограничением DTO, что гарантирует корректность keyset cursor. Все команды создания, переподчинения и архивации категории получают `pg_advisory_xact_lock(1398031445, 3)` до чтения дерева/состояния и сериализуют parent/archive/create races. Они блокируют затронутые category rows `FOR UPDATE` в UUID-порядке и повторно проверяют состояние до commit. Каждый ненулевой `parentId` должен ссылаться на `ACTIVE` категорию; проверка выполняется под блокировкой родителя, иначе возвращается `CATEGORY_INACTIVE_PARENT`. Перед архивацией повторно проверяются активные children и current draft/pending/published pointers неархивных продуктов; старые non-current returned/rejected/superseded revisions не блокируют архив. Reparent затем использует recursive CTE и отвергает parent из собственного поддерева. Цикл -> 409 `CATEGORY_CYCLE`. Публичная навигация возвращает ACTIVE прямых детей страницами до 100 категорий; без `parentSlug` выбираются корни. Страницы используют keyset cursor по `(sortOrder, slug)`, поддерживаемый соответствующим индексом; recursive children и полный `total` не возвращаются. Клиент получает следующие страницы и уровни отдельными запросами. Создание/переименование категории и бренда не имеет отдельного review workflow и сразу меняет справочник после permission + audit.
- Product revision create/submit/publish повторно проверяют `ACTIVE` Brand, Category и нужные `AttributeDefinition` под `FOR SHARE` row locks до commit. Brand/category/attribute archive берёт конфликтующий `FOR UPDATE`, ждёт текущие writes, затем повторяет usage/child check; так параллельные публикация и архив не могут оба успешно зафиксировать несовместимое состояние. Справочники блокируются в устойчивом порядке таблиц и UUID.
- `ProductRelation` принадлежит конкретной source revision и ссылается одной composite FK `(targetRevisionId,targetProductId) -> CatalogProductRevision(id,productId)` на конкретную опубликованную target revision; типы только `ACCESSORY` и `COMPATIBLE_EQUIPMENT`. Self-link проверяется транзакционным guard, не межтабличным CHECK. При изменении связи и публикации source-редакции source и target roots блокируются `FOR UPDATE` в отсортированном UUID-порядке; затем проверяются distinct roots, ACTIVE target и точное совпадение `target.publishedRevisionId`. Архив/републикация target использует тот же row lock. Публичная карточка включает безопасную target card только пока target активен и всё ещё указывает на эту revision. Устаревшая связь не показывается; editor вручную создаёт и публикует новую source revision. Автоперепривязки, `ANALOG`, `SUBSTITUTE` и автосопоставления нет.
- `ProductMedia` и `ProductDocumentVersion` принадлежат revision и ссылаются на точный R1-002 `FileVersion.id`. FK не является ACL или правом скачивания. Проверяются существование, доступ сотрудника по действующей `files.metadata.read` object policy, допустимый metadata DTO и MIME allowlist для media. Ни upload, ни download, ни URL, storage key или FileVersion ID в Public DTO не добавляются.
- R1-002 FileObject может иметь только `PRIVATE | INTERNAL`, FileVersion сейчас только `UNCHECKED`, а FileLink связан только с продавцом. Поэтому в R1-004B публичные media/documents отсутствуют; любая ссылка на непроверенный/приватный файл исключена. Появление публичного документа/фото требует отдельного утверждённого безопасного file delivery contract и изменения этой границы до включения отображения.

## 7. Цена и внешний DTO

В `CatalogProduct` не хранится закупочная/продажная цена. До утверждённого актуального price source публичный `priceDisplay` всегда `{kind: "ON_REQUEST", label: "Цена по запросу"}`. Просроченная, выключенная или не подтверждённая цена также отображается `ON_REQUEST`; никаких последних известных значений. Появление `CONFIRMED` цены — контрактная интеграция с R1-007/R1-009, не часть миграций R1-004B.

Public endpoints сериализуют опубликованное содержимое только из `publishedRevisionId` у активного продукта. Исторические revision snapshots сохраняют brand/category name на момент создания для staff/audit истории, но public projection строит `brand.name` и `category.name` из текущих ACTIVE справочников, чтобы immediate rename из OD-004A-09 отражался сразу; slug остаётся прежним. Public category navigation возвращает постраничный список ACTIVE прямых детей: без `parentSlug` — корни, с точным slug активного родителя — его дети; порядок `sortOrder ASC, slug ASC`, `pageSize` 1..100 (default 24). Необязательный opaque unpadded base64url cursor кодирует последний `(sortOrder, slug)` tuple; `meta.nextCursor` равен `null` в конце, полного `total` и потолка номера страницы нет. Каждый ответ содержит только один уровень и не более `pageSize` элементов; неизвестный или архивный `parentSlug` даёт одинаковый 404. Клиенты строят дерево последовательными bounded requests. Draft/pending/returned/rejected и архивные products, категории и relations публичным API не раскрываются; неизвестный и недоступный product slug дают одинаковый 404. Public DTO не содержит cost, supplier/source, audit, staff IDs, внутренние комментарии, draft/status, FileVersion IDs, storage keys или internal file metadata.

## 8. Конкурентность, аудит и миграция

- OCC: каждая команда ссылается на ожидаемый `CatalogProduct.version` или версию справочника. Root row берётся `FOR UPDATE`; product revision create/submit/publish держит `FOR SHARE` на exact active references до commit, archive/state change конфликтует через `FOR UPDATE` и перепроверяет использование после ожидания. `FOR KEY SHARE` не используется как защита от смены неключевого `state`. Stale version -> 409 без изменения revision/audit success.
- Category reparent — сериализованный advisory lock до чтения дерева. Product submit/publish/archive/relations/media/documents и их audit insert транзакционны. При ошибке audit — полный rollback данных и pointers, HTTP 503 `AUDIT_UNAVAILABLE`.
- Audit хранит action, entity type/id, requestId, actor, changed field names, revision IDs и bounded decision reason. Не записывать полные описания, тексты документов, PII, файлы или финансовые сведения в JSON audit payload. Значения редакции и автора остаются восстанавливаемыми по неизменяемым revisions.
- R1-004B migration additive: сначала проверить успешную FROZEN R1-002 1.0.0 schema; зарегистрировать catalog permissions без `RolePermission` assignment; создать таблицы/FK/RESTRICT/CHECK, включая partial unique indexes на один `DRAFT`/`PENDING_REVIEW`, expression indexes с `COLLATE "C"`, bounded `varchar(240)` и transaction/trigger guards для статусов и межтабличных invariants; append-only расширить audit action/entity validation без изменения файлов R1-002; только затем код API. Не включать миграцию в startup и не применять к production этим контрактом.
- Нет destructive down migration для заполненной БД: rollback приложения оставляет additive schema и данные; migration rollback acceptance выполняется на одноразовой копии/фикстуре и подтверждает обратную совместимость старого приложения плюс backup/restore сохранность sentinel rows. Удаление реальных catalog rows/таблиц не является автоматическим rollback.
