# R1-007 Contract Acceptance Matrix — Proposed 0.1.0

| ID     | Scenario                                                                          | Required result                                                                                                                                        | Verification                                                                               |
| ------ | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| SUP-01 | Create supplier with only provided fields                                         | Active supplier, first immutable profile revision and audit commit atomically; missing legal/contact data stays null                                   | PostgreSQL HTTP integration                                                                |
| SUP-02 | Create offer without a catalog match                                              | Offer and immutable first revision persist with null current match                                                                                     | PostgreSQL HTTP integration                                                                |
| SUP-03 | Two or more suppliers offer the same physical SKU                                 | Independent offers can point to one product; no uniqueness/merge across suppliers                                                                      | PostgreSQL HTTP integration                                                                |
| SUP-04 | Create and approve an exact match manually                                        | Proposal is PENDING until one staff decision; approval records identity snapshot and audit                                                             | PostgreSQL HTTP integration                                                                |
| SUP-05 | Reject one proposal                                                               | Proposal becomes terminal REJECTED; retry cannot turn it APPROVED                                                                                      | PostgreSQL HTTP integration                                                                |
| SUP-06 | Same name / similar text, different original part or manufacturer                 | No exact candidate and no automatic association                                                                                                        | Contract + HTTP integration                                                                |
| SUP-07 | Modification missing/unknown versus product modification absent                   | `UNKNOWN` is not equal to NULL; no approval without explicit evidence that modification is absent                                                      | Contract + HTTP integration                                                                |
| SUP-08 | Offer passes freshness cutoff                                                     | Historical revision remains; staff view explicitly says STALE; never represents it as current                                                          | Unit + PostgreSQL HTTP                                                                     |
| SUP-09 | Read public catalog/quotation endpoints with supplier data present                | No supplier contacts, offer fields, purchase costs, provenance or internal match data in public DTO/cache                                              | Public HTTP black-box; E2E-02 regression                                                   |
| SUP-10 | Staff lacking any required permission                                             | Server denies the action; UI hiding is not used as authorization                                                                                       | HTTP permission matrix                                                                     |
| SUP-11 | Concurrent offer edit / decision / product identity change                        | OCC or exact identity revalidation rejects stale command; no lost update/partial link                                                                  | Real PostgreSQL concurrency test with final row/audit state                                |
| SUP-12 | Approve or reject a proposal                                                      | Audit identifies actor, UTC time, offer/product/proposal and reason code without leaking costs/source text                                             | PostgreSQL audit assertion                                                                 |
| SUP-13 | Change offer price after an approved quotation snapshot exists                    | Supplier revision changes only; approved quotation snapshot and PDF remain unchanged; no side effect invokes quote recalculation                       | Regression test; if quote module absent, explicit no-integration/no-public-price assertion |
| SUP-14 | Replace or explicitly unlink a mistaken approved match                            | One current pointer only; prior approved decision remains history; unlink requires reason and audit                                                    | PostgreSQL HTTP integration                                                                |
| SUP-15 | Compare offers in multiple currencies                                             | Amounts are grouped by currency; no conversion, ranking across currencies or automatic source choice                                                   | API + UI integration                                                                       |
| SUP-16 | Archive supplier with existing offers                                             | History retained; no new offer/edit; archived supplier's offers excluded from current comparison                                                       | PostgreSQL HTTP integration                                                                |
| SUP-17 | Retry with same idempotency key and payload / reuse key with different payload    | Same command returns same result; key reuse with different body conflicts; no duplicate revision/decision/audit                                        | PostgreSQL HTTP integration                                                                |
| SUP-18 | Edit supplier contacts/requisites/notes                                           | New immutable SupplierRevision is visible to permitted staff; prior values remain reconstructable; AuditEvent contains names only                      | PostgreSQL HTTP integration                                                                |
| SUP-19 | Create two ACTIVE suppliers with the same normalized tax identity                 | Second create returns `SUPPLIER_IDENTITY_CONFLICT`; DB partial unique index prevents concurrent duplicates                                             | PostgreSQL HTTP concurrency integration                                                    |
| SUP-20 | Re-register the tax identity of an ARCHIVED supplier                              | New ACTIVE supplier gets a new ID and separate history; archived row remains unchanged; no unarchive/merge                                             | PostgreSQL HTTP integration                                                                |
| SUP-21 | RU and foreign tax identity validation                                            | RU accepts only checksum-valid 10/12 ASCII digits and preserves leading zeroes; foreign identity uses NFC/U+0020 trim only                             | Contract validation + unit + PostgreSQL                                                    |
| SUP-22 | Recreate a proposal for the same pair after REJECTED or APPROVED then UNLINK      | Old decision/link history is unchanged; new proposal has a new ID and audit; only one current pointer                                                  | PostgreSQL HTTP integration                                                                |
| SUP-23 | Submit concurrent duplicate PENDING proposals for the same offer/revision/product | At most one PENDING row commits; loser gets stable conflict; terminal history is not constrained by tuple uniqueness                                   | Real PostgreSQL concurrency test                                                           |
| SUP-24 | Same idempotency key concurrently and after API restart                           | One command/result is persisted; retries return identical saved status/body without another revision, proposal or audit                                | PostgreSQL HTTP integration + process restart                                              |
| SUP-25 | Retry exact command after VERSION_CONFLICT; then correct expected version         | Same key replays saved 409; corrected request needs a new key and can proceed; failed OCC has no domain write/success audit                            | PostgreSQL HTTP integration                                                                |
| SUP-26 | Reuse a key across routes or with a different canonical payload                   | Same actor/scope key is global to R1-007; mismatched hash returns `IDEMPOTENCY_KEY_REUSED`; no duplicate domain result                                 | PostgreSQL HTTP integration                                                                |
| SUP-27 | Sort and paginate prices in multiple currencies                                   | Currency groups sort by ISO code `COLLATE "C"` ascending; decimal price sorts only within group; deterministic keyset cursor uses full tie-break tuple | API + PostgreSQL contract integration                                                      |
| SUP-28 | Store `manufacturerName` at the frozen R1-004 maximum                             | Exactly 200 characters is accepted and remains exact-matchable; 201 is rejected; R1-004 schema/files are unchanged                                     | Contract + PostgreSQL integration                                                          |
| E2E-05 | Two visually similar catalog products                                             | No link without exact R1-004 identity tuple and an individual admin decision                                                                           | Full staff UI + API E2E                                                                    |

Contract checks additionally assert: no public paths in supplier OpenAPI; no business CRUD/migration implementation in R1-007A; no floats for money; exact existing R1-004 identity normalization; and no modifications to frozen R1-002/R1-004/R1-006A artifacts.
