# R1-006 — каталоговый CSV/XLSX импорт

**Статус: PROPOSED. Версия: 0.1.0-proposed.** Требует утверждения владельца до миграций и реализации. Основание: CAT-02/CAT-05, E2E-03, решения №6, 25 и 56, FROZEN R1-002 1.0.0 и FROZEN R1-004 1.0.0. Этот контракт дополняет каталог и не меняет frozen артефакты.

## 1. Границы

R1-006 — ручной staff-процесс импорта товарной номенклатуры. Он не является SupplierOffer/источником поставщика R1-007…009 или SourceDocument/импортом клиентской спецификации R1-010…013. Нет crawling, расписаний, цен, остатка, заказов, PDF/OCR, подбора аналогов, массового решения, публикации или public import API.

NestJS остаётся единственным владельцем RBAC, состояния импорта, сопоставления с каталогом, решений, продуктовых ревизий и аудита. Уже существующий FastAPI ingestion service получает только ограниченный поток файла по внутренней сети и возвращает ограниченные ячейки/координаты/ошибки. У него нет PostgreSQL/Redis credentials, доступа к StoragePort, продуктовых команд или полномочий принимать решения.

## 2. Предлагаемая модель

Добавить ровно три таблицы. UUIDv4, timestamptz(6), FK RESTRICT, обычные транзакции PostgreSQL и Prisma Migrate следуют FROZEN R1-002/ADR-001.

### CatalogImportRun

- id UUID PK, uploaderStaffUserId UUID FK StaffUser, sourceFileObjectId UUID, sourceFileVersionId UUID, sourceFormat enum CSV/XLSX, sourceEncoding/sourceDelimiter nullable enums, bounded sourceParseIssues JSONB, parserVersion varchar(32), state enum, mapping JSONB, mappingVersion int32, uploadIdempotencyKey UUID, uploadRequestHash bytea(32), version int32, createdAt/updatedAt timestamptz(6);
- UNIQUE(uploaderStaffUserId, uploadIdempotencyKey); composite FK (sourceFileVersionId, sourceFileObjectId) -> FileVersion(id, fileObjectId); FK RESTRICT. Source checksum, size, MIME and original filename are derived from the immutable FileVersion; they are not copied into a second mutable authority.
- Upload accepts the file plus optional CSV encoding/delimiter choices, runs the bounded parser before committing the FileObject/FileVersion, and persists parsed raw rows in the same PostgreSQL transaction as the run and success audit. A successful upload starts at SOURCE_READY or SOURCE_PARTIAL; malformed files or hard-limit violations are rejected before a run/FileVersion is created. The parser does not decide product fields.
- state: SOURCE_READY | SOURCE_PARTIAL -> MAPPED -> PREVIEWING -> PREVIEW_READY | PREVIEW_PARTIAL -> COMPLETED | COMPLETED_WITH_ISSUES. Mapping correction returns an unresolved run to MAPPED and increments mappingVersion. PREVIEW_PARTIAL can retry against immutable stored raw rows. COMPLETED means every included data row is APPLIED or REJECTED; COMPLETED_WITH_ISSUES means at least one included data row remains invalid, held, conflicting, duplicate, unmapped or otherwise not accepted, or sourceParseIssues is non-empty. Re-preview may resolve HELD/CONFLICT rows; state is a summary, not a destructive lock.
- sourceParseIssues contains at most 256 bounded code/message records (16 KiB total), never raw bytes/cells. Run rowCounts are derived: total counts persisted non-empty source rows including headers; header/ignored are mapping classifications; sourceInvalid counts parser-invalid rows; invalid counts mapped validation failures; ready counts NEW/EXACT_MATCH/NO_DEDUP_KEY rows; applied/held/rejected count their matching states.
- Mapping is bounded JSONB <=2 MiB, validates against schemaVersion 1, and records per-sheet header rows, optional fixed ACTIVE category/brand IDs, source column targets and explicit reference maps. CSV delimiter/encoding are immutable run fields fixed at upload and are not part of `ImportMappingRequest`. Mapping changes require expectedVersion and are allowed while the run has no APPLIED or REJECTED rows.

Mapping описывает отдельную header row и назначения колонок для каждого включённого листа, назначения колонок в фиксированные поля CatalogProduct/CatalogProductRevision и явные справочные сопоставления исходных значений к ACTIVE Brand/Category IDs. Для каждого листа можно задать `fixedCategoryId` и, при необходимости, `fixedBrandId`; тогда колонка соответствующего поля не требуется. Fixed ID и любое column/reference mapping для того же target одновременно запрещены и дают `400 VALIDATION_ERROR`. Fixed IDs и явные reference maps должны указывать на существующие ACTIVE сущности. У разных листов могут быть разные категории/бренды. Категория обязательна для каждой принимаемой строки: её источник — fixed ID либо явное mapping категории; если значение не разрешено, строка остаётся невалидной/NEEDS_MAPPING. При fixedCategoryId каждое attribute mapping обязано использовать ровно этот categoryId; разные определения других категорий не наследуются. Лист, отсутствующий в mapping, остаётся видимым как source-only, его строки имеют состояние IGNORED и не могут получить решение. CSV encoding/delimiter фиксируются при upload, сохраняются неизменно в run и включаются в upload request hash. Если encoding не задан, применяется UTF-8 (с распознаванием BOM); invalid UTF-8 возвращает ENCODING_REQUIRED, а Windows-1251 принимается только при явном выборе. Delimiter comma/semicolon/tab определяется только при однозначном результате; при неоднозначности загрузка возвращает VALIDATION_ERROR, и повторяется с явным delimiter и новым ключом идемпотентности. Справочные source values сравниваются только точно после Unicode NFC и удаления внешних U+0020 пробелов; без case-folding/fuzzy. Атрибуты назначаются точному AttributeDefinition ID, ограниченному его categoryId; одну source column можно явно связать с разными definition IDs для разных категорий. Никакого создания/архивации справочников из импорта. Одинаковый AttributeDefinition.code в другой категории не наследуется.

В одном включённом листе scalar targets (`displayName`, `summary`, `description`, `brandId`, `manufacturerName`, `originalPartNumber`, `modification`, `categoryId`) задаются не более одного раза. Для target=attribute обязательны exact `categoryId` + `attributeDefinitionId`; повтор одной пары `(columnIndex, categoryId, attributeDefinitionId)` запрещён. Одна source column может быть явно привязана к разным definitions по разным категориям, и для каждой строки используется только definition её mapped category. Неактивные/не принадлежащие этой категории reference IDs отклоняются при mapping и повторно проверяются при preview/decision. Заголовки не сопоставляются автоматически.

### CatalogImportRow

- id UUID PK, importRunId UUID FK CatalogImportRun, sheetIndex int32 >=0, sheetName varchar(128) nullable, sourceRowNumber int32 >=1, sourceCells/normalizedCandidate/validationIssues/warnings JSONB, candidateState enum, matchedProductId UUID nullable, expectedProductVersion int32 nullable, expectedCurrentRevisionId UUID nullable, version int32, createdAt/updatedAt timestamptz(6);
- UNIQUE(importRunId, sheetIndex, sourceRowNumber); all FKs RESTRICT. JSON payloads have application and database byte-size checks; raw cells are typed and bounded. Full source bytes remain the authoritative raw record.
- After source parsing, candidateState is NEEDS_MAPPING; the selected header row becomes HEADER when mapping is saved, and rows on omitted sheets become IGNORED. Other states: INVALID, NEW, EXACT_MATCH, NO_DEDUP_KEY, DUPLICATE_IN_RUN, ARCHIVED_MATCH, CONFLICT, APPLIED, REJECTED, HELD. HEADER/IGNORED/INVALID/NEEDS_MAPPING/DUPLICATE_IN_RUN/ARCHIVED_MATCH cannot be ACCEPTed. HELD and CONFLICT may be re-previewed; APPLIED and REJECTED are terminal.

sourceCells сохраняет ограниченное, типизированное представление исходных ячеек, включая исходный текст, номер колонки, тип XLSX-ячейки и формулу как текст, если она была. Эти строки доступны через staff rows API до выбора header/mapping только в пределах owner scope из §5; normalizedCandidate до preview является пустым partial object. Для CSV sourceRowNumber означает логический CSV record number (многострочное quoted поле — одна запись), для XLSX — исходный 1-based номер строки листа. Полностью пустые строки пропускаются, физические/логические координаты последующих строк не перенумеровываются. Полный оригинал остаётся в FileVersion. Неограниченное содержимое/архив не копируется в audit.

### CatalogImportDecision

Append-only запись на каждую уникальную команду решения: id, rowId, actorStaffUserId, idempotencyKey, requestHash, expectedRowVersion, mappingVersion, action (ACCEPT_CREATE, ACCEPT_REVISION, REJECT, HOLD), outcome (APPLIED, REJECTED, HELD, CONFLICT), conflictCode? (IMPORT_ROW_CONFLICT, IDENTITY_CONFLICT), targetProductId?, resultRevisionId?, reasonCode?, auditEventId, createdAt. UNIQUE(rowId, idempotencyKey). Same-key/same-hash retry возвращает сохранённый результат без второй Decision или AuditEvent; same-key/different-hash возвращает 409 IDEMPOTENCY_KEY_REUSED без новой Decision. Для outcome=CONFLICT `auditEventId` указывает на DENIED `catalog.import.row.decided` event; targetProductId/resultRevisionId отсутствуют. AuditEvent остаётся отдельным cross-cutting журналом actor/action/requestId и записывается атомарно с соответствующим результатом.

Все поля имеют UUIDv4/int32/timestamptz(6)/bounded varchar типы; UNIQUE(rowId, idempotencyKey), FK row/actor/audit/product/revision RESTRICT. requestHash — bytea(32), reasonCode — необязательный finite code без текста пользователя. Таблица append-only для runtime DB role. Точные машинные поля и ограничения зафиксированы в [data model](R1-006-catalog-import-data-model.json); actions/entity/outcomes — в [audit registry](R1-006-catalog-import-audit-registry.json).

Успешное ACCEPT_CREATE создаёт существующие CatalogProduct + DRAFT CatalogProductRevision через те же доменные правила R1-004B. ACCEPT_REVISION создаёт новую DRAFT revision существующего exact-match товара с теми же правилами OCC/base revision. Существующие таблицы каталога не заменяются и не дублируются. Ни одна команда импорта не вызывает submit/review/publish.

## 3. Файл и безопасный разбор — на утверждение

Использовать только существующий приватный volume и StoragePort. `POST /v1/staff/catalog/imports` принимает файл и необязательные `csvEncoding`/`csvDelimiter`; после parser success bytes записываются в private storage, затем FileObject/FileVersion metadata, run, raw ImportRows и success AuditEvent фиксируются одним PostgreSQL transaction. PRIVATE FileObject принадлежит uploader; FileVersion содержит фактический размер, SHA-256, allowlisted MIME, sanitized safe filename и safetyState UNCHECKED. Если transaction откатывается после object write, компенсируется только точный key при подтверждённом receipt текущего write; иначе остаётся диагностированный private orphan. Никакой FileObject/FileVersion/run не создаётся при parser отказе или hard-limit violation. Upload bytes нельзя скачать, привязать к ProductMedia/ProductDocumentVersion или выдать через public API; StorageKey и FileVersion ID не возвращаются в DTO.

Parser вызывается NestJS синхронно через private-network-only `POST /internal/v1/catalog-import/parse` существующего FastAPI ingestion app: Nest передаёт bounded byte stream, исходный safe filename, объявленный MIME и CSV options; ответ — UTF-8 NDJSON без BOM, `Content-Type: application/x-ndjson`, одна JSON запись на строку, завершённую LF. Допустимы только записи с фиксированными полями: `START={type,protocolVersion,sourceFormat}` (ровно одна, первая; version=1; format CSV/XLSX); `SHEET={type,sheetIndex,sheetName}` (индексы 0–19, имя не более 128 code points или null; ровно одна на лист до его строк); `ROW={type,sheetIndex,sourceRowNumber,cells}` (номер строки >=1, coordinates unique), где cells — массив не более 128 элементов `{columnIndex,cellType,rawValue,numberFormat?}`; columnIndex 0–127, `cellType` из `TEXT|NUMBER|BOOLEAN|FORMULA|BLANK`, `rawValue` не более 4 000 code points и `numberFormat` не более 64 code points. Значения — только исходное ограниченное инертное представление, формулы никогда не исполняются. Terminal: `COMPLETE={type,parserVersion,sourceParseIssues:[]}` или `PARTIAL={type,parserVersion,sourceParseIssues:[{code,message}]}`; parserVersion не более 32 chars, PARTIAL содержит 1–256 issue records, а весь массив не более 16 KiB. Поля сверх перечисленных запрещены; каждая ROW ссылается на ранее объявленный SHEET, source coordinates не повторяются, пустые NDJSON lines запрещены. Ровно одна терминальная запись обязательна и должна завершиться LF; после неё не допускаются данные или другая запись.

HTTP transport chunk boundaries произвольны и не являются границами записей. Nest буферизует неполную строку, валидирует UTF-8/JSON и применяет logical batch bounds: максимум 250 `ROW` records и 4 MiB сериализованных байтов на batch; одна `ROW` запись максимум 1 MiB, START/SHEET/terminal записи максимум 16 KiB. Ограничения не заменяются Content-Length/ZIP metadata. Если поток оборван, не содержит валидного терминала, содержит неверный порядок/тип/кодировку, превышает line/batch/record bounds или имеет два терминала, весь ответ считается `INGESTION_UNAVAILABLE` (503): Nest отбрасывает все полученные parse results и не создаёт FileObject, FileVersion, ImportRun или ImportRows. Превышение file-wide bounds — отдельный отказ upload до создания данных; структурная ошибка после валидных строк завершается PARTIAL. Parser timeout — 15 s на весь файл. Python не имеет доступа к PostgreSQL, Redis, file volume, staff credentials или бизнес-командам, не создаёт нормализованные товарные значения и не возвращает storage keys. Endpoint не публикуется на host/public interface; NestJS остаётся единственной точкой авторизации и сохранения. Перед production фиксацией лимита R1-006B проверяет 15 s на представительных и near-bound fixtures; если лимит непрактичен, реализация останавливается до изменения контракта владельцем.

ADR-004 требует определить quarantine/scanning до upload. Рекомендуемая узкая граница: это не generic file upload и не заявка на malware-cleared файл; исходник постоянно остаётся UNCHECKED/quarantined и допускается только на bounded, no-execution parser path. Его нельзя использовать или распространять вне импорта. Это требует явного принятия владельцем ограничения «структурная проверка формата вместо антивирусного заключения»; файл не маркируется безопасным.

Рекомендуемые hard bounds начального профиля сохраняются: upload <=10 MiB; XLSX ZIP entries <=256 и суммарно фактически распакованные данные <=50 MiB; <=20 листов, <=20 000 непустых строк всего и <=128 колонок; mapped text cell <=4 000 Unicode code points; parsing timeout 15 s на файл. Лимиты проверяются по фактически прочитанным потокам, не только по ZIP metadata. Превышение общего лимита — отказ файла до создания run. Ошибка одной строки после bounded parsing не отменяет остальные preview rows. Практичность 15 s проверяется на тестовых файлах в R1-006B; значение нельзя тихо увеличить при реализации.

CSV MIME allowlist: text/csv, application/csv, text/plain или application/octet-stream только для файла .csv с валидным текстовым содержимым. XLSX MIME allowlist: application/vnd.openxmlformats-officedocument.spreadsheetml.sheet или application/octet-stream для .xlsx с валидной OOXML/ZIP-структурой. Extension, declared MIME и содержимое проверяются совместно. XLSM/embedded VBA, malformed package и external relationship content отклоняются; external links никогда не запрашиваются. CSV: UTF-8/UTF-8 BOM распознаётся; Windows-1251 допустим только при `csvEncoding=WINDOWS-1251`; неизвестная/некорректная кодировка отклоняется с ENCODING_REQUIRED/INVALID_ENCODING, без догадки. Delimiter comma, semicolon или tab определяется только при однозначном результате, иначе сотрудник выбирает `csvDelimiter` при upload. XLSX не принимает CSV options. XLSX: формулы не исполняются; формульная ячейка в mapped поле получает ошибку и не подставляет cached value. Text part numbers сохраняются буквально. Числовой XLSX part number принимается только для целого безопасного значения, когда формат ячейки состоит из нулей; нули восстанавливаются по ширине формата, добавляется предупреждение. Иные числовые identity cells отклоняются, не округляются и не преобразуются из scientific notation.
Raw filenames and cell values are always treated as inert text in staff UI/API: render escaped text only, never interpret HTML, formulas, markdown, links, or embedded content. The source file itself has no download route.

## 4. Сопоставление, ручное решение и конкурентность

- Совпадение — только FROZEN R1-004 identity tuple (brandId, manufacturerName, originalPartNumber, modification) и его нормализация. Название товара, похожесть, AI и нечёткий search не служат основанием для match. NULL modification остаётся отличным от любого значения.
- Неполный identity tuple даёт NO_DEDUP_KEY: автоматического совпадения нет; создание допускается только отдельным ACCEPT_CREATE по этой строке, поэтому штатное ограничение/конфликт R1-004 всё равно окончательно применяется в транзакции.
- Точное совпадение с archived product даёт ARCHIVED_MATCH; импорт не восстанавливает товар и не создаёт дубль. Повтор identity в файле помечается DUPLICATE_IN_RUN; строки не сливаются автоматически.
- Сразу после upload uploader видит bounded raw cells всех непустых строк и исходные координаты до выбора mapping. `PUT mapping` назначает header row, fixed category/brand или source columns для каждого включённого листа; неуказанные листы остаются видимыми владельцу как source-only/IGNORED. `POST preview` применяет сохранённый mapping к raw rows, выполняет validation и exact identity lookup, возвращая нормализованные поля, category/attribute errors, warnings, exact match, observed product version/current revision и предполагаемое действие.
- Каждая строка получает собственную команду ACCEPT_CREATE, ACCEPT_REVISION, REJECT или HOLD. Нет batch command. HOLD не меняет каталог и оставляет строку для последующей работы по правилам повторного preview/решения.
- Mapping можно менять с expectedVersion, пока в run нет APPLIED или REJECTED rows. MappingVersion увеличивается; нерешённые rows нормализуются заново из immutable sourceCells, а прежние HOLD/CONFLICT decision events остаются в истории. После первой APPLIED/REJECTED mapping frozen. Preview повторяем с тем же source и mapping; координатный UNIQUE предотвращает дублирование и не переписывает terminal decisions. Разные листы имеют отдельные header rows/column maps. Неизвестное справочное значение оставляет row в NEEDS_MAPPING; сотрудник может добавить явный reference map и повторить preview до terminal decision.
- ACCEPT_CREATE и ACCEPT_REVISION сначала выполняются в одной транзакции с блокировкой ImportRow и каталожной цели. NestJS повторно проверяет expectedRowVersion, expectedProductVersion/current revision, identity, ACTIVE references и текущую state machine. Если операция проходит, каталоговое изменение, row update, одна Decision `APPLIED` и success AuditEvent коммитятся вместе; ошибка success audit откатывает всё.
- Если ACCEPT_CREATE/ACCEPT_REVISION обнаруживает stale catalog target/state или identity uniqueness conflict, первая транзакция целиком откатывается: она не оставляет продукт, revision, pointer или success AuditEvent. Затем под той же row/idempotency serialization выполняется conflict-record transaction: если ключ ещё не использован, она атомарно устанавливает `CatalogImportRow.candidateState=CONFLICT`, вставляет ровно одну `CatalogImportDecision.outcome=CONFLICT` с точным `conflictCode` и null target/revision IDs и связывает её с `catalog.import.row.decided` DENIED AuditEvent (`IMPORT_ROW_CONFLICT` или `IDENTITY_CONFLICT`). Только после commit этой транзакции API отвечает HTTP 409 с тем же стабильным кодом. Если запись denial audit не удалась, conflict-record transaction откатывается целиком, API возвращает 503 AUDIT_UNAVAILABLE, а каталожного изменения не остаётся. Конфликт не создаёт успешный audit.
- Идемпотентность проверяется до повторной доменной обработки: тот же row/key/hash возвращает сохранённый 409 с тем же `conflictCode` и существующую Decision, без второй Decision или AuditEvent; тот же ключ с другим hash возвращает 409 IDEMPOTENCY_KEY_REUSED без новой Decision. Stale expectedRowVersion/mappingVersion — отдельный VERSION_CONFLICT: состояние строки и история решений не меняются. ACCEPT_REVISION допустим только для текущего exact-match активного товара и если существующая state machine допускает новую DRAFT revision.
- Owner-only PRIVATE file bytes не возвращаются staff/public API и не скачиваются; parser получает stream только на authorized upload. После создания run для preview/resume используются сохранённые raw rows, повторное чтение FileVersion не требуется. Между private storage и PostgreSQL нет общей транзакции: если DB transaction падает после успешного object write, файл остаётся private orphan и не является успешным импортом, если точечная компенсация exact newly-written key не подтверждена receipt текущего вызова StoragePort. Запрещены wildcard cleanup и удаление committed FileVersion; неуспешная компенсация диагностируется, а запрос остаётся неуспешным.
- Upload requestHash — SHA-256 over uploader identity scope, content SHA-256, source format, sanitized original filename, declared MIME and normalized CSV options; row-decision hash includes actor, row, action, reasonCode and expected row/product/current-revision versions. Repeating the same key and hash returns the stored result; the same key with another hash returns 409 IDEMPOTENCY_KEY_REUSED. Mapping uses expectedVersion; preview is serialized by a run lock and idempotent upsert by row coordinate. Distinct rows are never accepted in one transaction.
- Незавершённые run/preview возобновляются чтением сохранённых строк и повтором preview; повторное чтение источника Python parser не требуется. Redis queue/job не добавляется. Частичная ошибка строки при первичном разборе сохраняет остальные валидные исходные строки и переводит run в SOURCE_PARTIAL; ошибка строки при применении mapping даёт PREVIEW_PARTIAL.

## 5. API и RBAC

Machine-readable контракт: [R1-006-catalog-import.openapi.json](R1-006-catalog-import.openapi.json). Все маршруты только staff, с frozen R1-002 session cookie, точным Origin, X-CSRF-Token на изменяющих запросах, X-Request-Id и Cache-Control: no-store. Public API не содержит импортов или исходных строк. По умолчанию сотрудник с `catalog.products.read` видит только импортные run/rows, где он uploader; `catalog.products.read` не раскрывает raw source rows всей организации. Свой run можно изменять при `catalog.products.read` + `catalog.products.write`; mapping, preview и decision также требуют `catalog.references.read`, потому что читают или повторно проверяют Brand/Category/AttributeDefinition. ACCEPT_CREATE/ACCEPT_REVISION дополнительно проходят существующую catalog product write command.

Новых permission codes не вводить и не менять frozen bootstrap/protected permission sets. Upload требует `catalog.products.read` + `catalog.products.write`; mapping/preview/row decision — эти два права плюс `catalog.references.read`; GET — `catalog.products.read` и ownership check. Не-owner list/read/rows/history доступен только ACTIVE сотруднику, чья эффективная union permissions содержит все `controlAdminRequiredPermissions` из FROZEN R1-002 и `catalog.products.read`. Изменение чужого run или решение чужой строки дополнительно требует `catalog.products.write` и `catalog.references.read`. Проверяется effective permission union, не имя роли. GET list по умолчанию возвращает только свои run; параметр `ownerStaffUserId` разрешает запрос чужого списка только по read-правилу. Недоступный чужой run/row возвращает 404. Cross-owner чтение и действия фиксируются отдельным `catalog.import.cross_owner.accessed`; при изменении он коммитится в одной транзакции с обычным audit и изменениями. Уполномоченный администратор может читать историю и решать отдельную чужую строку; generic product read сам по себе этого права не даёт. Файловых GET/download нет; исходные bytes передаются только bounded parser при авторизованной upload операции.

Операции: POST upload, GET run list, GET run, PUT mapping, POST preview/resume, GET paged rows, POST row decision, GET row decision history. Cursor/page bounds аналогичны staff catalog list. DTO, errors, idempotency, request sizes и permissions закреплены в OpenAPI.

## 6. Audit и ошибки

Добавить append-only codes отдельным R1-006 registry artifact, не редактируя R1-002/R1-004 registries: entity types CatalogImportRun/CatalogImportRow; actions catalog.import.created, catalog.import.mapping.changed, catalog.import.preview.completed, catalog.import.row.decided и catalog.import.cross_owner.accessed. Успешные каталожные изменения атомарны с Decision и success AuditEvent. Business conflict возвращает HTTP 409 только после rollback каталожной попытки и отдельного атомарного commit строки CONFLICT, Decision outcome=CONFLICT и DENIED AuditEvent; эта запись не считается success audit. Audit failure откатывает соответствующую транзакцию и не допускает ложный успех. Cross-owner read/mutation audit содержит owner/run/row IDs и accessKind. В AuditEvent changes — только IDs, row coordinate, mapping/version/state, decision/result и changed field names; без полных raw/normalized cells, содержимого файла и storage key.

Ошибки/статусы: 401/403 frozen auth semantics; 400 VALIDATION_ERROR, ENCODING_REQUIRED, INVALID_ENCODING, FILE_REJECTED; 404 unknown/unauthorized; 409 VERSION_CONFLICT, IMPORT_ROW_CONFLICT, IDEMPOTENCY_KEY_REUSED, IDENTITY_CONFLICT; 413 FILE_TOO_LARGE/IMPORT_LIMIT_EXCEEDED; 415 UNSUPPORTED_MEDIA_TYPE; 503 INGESTION_UNAVAILABLE/AUDIT_UNAVAILABLE. DTO не включает абсолютные пути, storageKey, stack traces или неразрешённые product fields.

## 6.1 Retention — временное решение R1

В R1 источник, raw rows и decision history сохраняются бессрочно без автоматического удаления. Это временный контракт для пилотного R1 и не является достаточной политикой production retention. До production эксплуатации владелец должен утвердить срок и процедуру хранения/удаления, legal hold, права и аудит удаления, поведение ссылок/истории и последствия для приватных FileVersion. Без такой политики production эксплуатация импорта не начинается.

## 7. Версионирование и совместимость

Контрактный пакет additive: новые таблицы/индексы/append-only audit registry и новые staff import paths. Не менять FROZEN R1-002, R1-004 модели, каталожные DTO, product state machine, identity rules, protected permissions, опубликованный OpenAPI или публичный API. Миграция в B проверяется на пустой и fixture DB; production migrate/deploy не разрешены этим контрактом.
