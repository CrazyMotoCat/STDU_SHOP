**R1-002 2.0.0-draft.1 и R1-004 2.0.0-draft.1 · NOT FROZEN.** R1-004 draft зависит от R1-002 draft и от выбора политики CD-01. Существующие [R1-002 V1](../R1-002-staff.openapi.json), [R1-004 V1](../R1-004-catalog.openapi.json) и [ADR-004](../../adr/ADR-004-file-storage.md) остаются действующими. Точные OpenAPI, machine-readable schemas, grants и миграции проходят отдельное утверждение после proof. [Решения владельца](../../plans/VIS-CAT-02A-CONTRACT-DECISION.md).

## R1-002 2.0.0-draft.1 · storage и аудит

- Серверный enum FileVersion namespace `DEFAULT | CATALOG_MEDIA_SOURCE | CATALOG_MEDIA_DERIVATIVE`. Существующие FileVersion остаются DEFAULT. Оба новых namespace остаются PRIVATE, без generic metadata/download и без прямого storage доступа worker/verifier. FileVersion источника и производной неизменяемы. В проекте обе FileVersion остаются UNCHECKED в обоих вариантах CD-01. В варианте scanning результат хранится в отдельном media-gate с привязкой к digest и не меняет generic safetyState. R1-010D и его state machine не меняются.
- StorageIntent владеет точными staged/final ключами, ingestion/job, поколением, lease, digest и byte count. Только media adapter знает ключи. Перед записью резервирует intent. Перед транзакцией READY синхронизирует файл и каталоги и атомарно устанавливает финальный immutable объект без замены. READY, актуальный fencing token, manifest, FileVersion и результат аудита фиксируются одной транзакцией. Публичная доступность при ошибке закрыта.
- SYSTEM audit — закрытый actor с внутренним service identity `CATALOG_MEDIA_ORCHESTRATOR`, без staff identity, с FK на exact attempt/intent и проверяемым action/resource/outcome. Финитный набор: `MEDIA_ATTEMPT_VERIFIED`, `MEDIA_ATTEMPT_REJECTED`, `MEDIA_SET_UNAVAILABLE`, `MEDIA_INTENT_RECONCILED`. Пишет только NestJS на основании проверенного состояния. Идемпотентность по типу действия, цели и версии перехода. Payload ограничен target ID, correlation ID, кодом результата и временем; без bytes, paths, tokens, rights evidence. SYSTEM не пишет события человека и не транслирует произвольные строки worker. Изменение бизнес-состояния без обязательного audit откатывается. Независимый отказ обязательного storage audit не превращает ошибку выдачи в разрешение.

## R1-004 2.0.0-draft.1 · данные и lifecycle

Composite FKs связывают ProductMedia с exact product/revision/ingestion/source/set. Подтверждение товарного соответствия связывает продукт, ревизию, каноническую идентичность R1-004, set и manifest. READY/namespaces/visibility и права проверяются на submit/publish и на чтении опубликованной связи                     |

- Активация набора происходит только через штатную публикацию exact revision под блокировкой корня товара и OCC. Порядок блокировок для мутаций: product root, revision, media rows; права — единый порядок для операций, которые блокируют запись доказательства. Отзыв доказательства меняет центральную запись прав и audit одной транзакцией; публичное чтение всегда проверяет эту запись в той же MVCC snapshot. Операция прав не пытается захватывать product locks в обратном порядке. Блокировки не держатся во время файловых, сканирующих и сетевых операций. Старая ревизия хранится неизменной.
- Новая ревизия требует повторного подтверждения exact match. Новое поколение, изменения доказательства или идентичности требуют повторных относящихся к ним аттестаций. Revoke терминален на asset, исключает новые публичные запросы на все его поколения и не удаляет bytes. Staff preview отозванной или недоступной производной закрыт. Исправление после отзыва создаёт новый проверяемый актив.
- Рекомендуемая модель перехода — отдельная типизированная связь `CatalogRevisionMediaV2` при той же ревизии. Она имеет собственный порядок и primary. Существующий V1 PUT полностью заменяет только legacy-метаданные, как и раньше. Новый V2 код не меняет V1 GET, порядок, primary, errors и набор V1 файловых разрешений. Копирование черновика переносит V2 связи как непубличные и требует нового подтверждения идентичности. Если V1 публикует ревизию, непроверенная V2 связь остаётся невидимой в V2. Проверка V2 eligibility не вводит новых отказов для операций V1. До freeze проверить совместимость длинных сценариев copy → V1 replace → V2 attach → submit/publish/archive. Если совместимость не доказана, удерживать typed media отключённым и вынести отдельное контрактное решение.
- Legacy фото получают eligibility только через ручную re-ingestion, подтверждение прав и exact match. Автоматического backfill нет.

Если владелец выбирает scanning, допуск worker требует действительного media-gate для точного digest источника. Переход набора в READY требует действительных результатов для источника и всех производных. Staff preview, V2 image metadata и публичные GET/HEAD/304 заново проверяют действительность нужных media-gates в snapshot принятия решения. Истечение срока, отзыв или изменение политики закрывают доступ до повторной проверки. Сканирование и повторная проверка выполняются вне HTTP чтения и вне транзакций публикации. Замена байтов требует новой проверки, а verdict с тем же точным digest может использоваться повторно только в рамках одобренной политики свежести.

## Manifest, verifier и storage recovery

В проекте manifest version определяет закрытую схему, единственное каноническое представление и фиксированный порядок вариантов. API отвергает лишние/повторяющиеся поля и варианты, несовпадающие размеры, идентичность attempt и профиль, затем заново строит canonical manifest и считает его SHA-256. У worker и verifier отдельные процесс, сборка, права и ресурсный бюджет. Verifier получает точно те замороженные staged WebP, которые API намерен сохранить, и возвращает результат, связанный с job, attempt, profile/policy и списком точных digest. Источник для сверки не нужен. API проверяет тот же immutable объект перед переводом READY. Манифест содержит schema/policy/profile versions, exact source digest, и на вариант — enum, width, height, byte count, SHA-256. Opaque job/attempt/nonce находятся во внешнем конверте и связываются с manifest digest сервером.

Уникальные ключи staging/final зависят от намерения и поколения. Перезапуск может повторить чтение, классификацию и уже завершённый результат. Старый writer не перезаписывает ключи нового поколения и не может установить READY. Reconciler сначала фиксирует fence, затем доказывает отсутствие ссылок, live writers и удержаний перед удалением точного ключа; предполагаемые orphan остаются на месте при неясном ownership. Commit записывает только уже синхронизированные exact files. Отдельно учитывать отсутствующие файлы при restore и недоступность до проверки связанной копии БД и байтов.

## Вариант интерфейсов

Staff base `/v2/staff/catalog/products/{productId}`. Все операции требуют Staff session, `catalog.products.read` и объектный доступ к точному товару. Мутации используют штатные Origin/CSRF, OCC для изменяемых product/media state и idempotency для upload/process/revoke. Новые permissions выдаются явным решением, без автоматических грантов. Права upload/attach не дают preview, rights attestation или revoke автоматически. Ни SYSTEM, ни worker не получают Staff grants. Предлагаем не разрешать аттестацию прав сотруднику, зарегистрировавшему evidence для этой версии.

| ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /media-ingestions`                         | `catalog.products.media.upload`; поток одного файла и bounded typed metadata; `202 {ingestionId,state}`                                                                                                    |
| `GET /media-ingestions/{ingestionId}`            | `catalog.products.media.read`; безопасный статус и bounded reason code, без ключей и оригиналов                                                                                                            |
| `POST /media-ingestions/{ingestionId}/process`   | `catalog.products.media.upload`; допущенная попытка, `202`                                                                                                                                                 |
| `GET /media/{assetId}/{setId}/{variant}/preview` | `catalog.products.media.preview`; exact verified WebP, `private, no-store`; preview разрешён без статуса публичных прав для закрытой проверки, с обязательным объектным доступом                           |
| `POST /media-evidence`                           | `catalog.products.media.rights.write`; зарегистрировать закрытую версию evidence для exact ingestion/source digest, вернуть ограниченный ID/версию. Новая версия не заменяет принятую запись автоматически |

| `PUT /media/{assetId}/draft`                     | Действующее `catalog.products.media.write` и новое `catalog.products.media.attach`; exact draft, set и поля отображения, ручная аттестация идентичности, OCC                                               |

Preview, права, attach и revoke имеют отдельные человеческие audit actions при соответствующей мутации; publish остаётся существующим полномочием `catalog.products.publish`. Проект ошибок Staff: 401 без сессии, 403 без полномочия, 404 для отсутствующего/чужого объекта после проверки роли, 409 для OCC/replay/state conflict, 413 для превышения limits, 415 для формата, 503 для недоступной обязательной зависимости. Доступ аудитора к закрытым доказательствам проверяется отдельным разрешением на уровне объекта.

Публичный API `GET /v2/public/catalog/products` и `GET /v2/public/catalog/products/{slug}` сохраняет форму публичного каталога с дополнительными `primaryImage: null | MediaImage` и `images: MediaImage[]` соответственно. `MediaImage` содержит только `publicAssetId,renditionSetId,altText,width,height,aspectRatio,variants`. Variants выдаются фиксированным ключевым набором профиля со своими dimensions, MIME и same-origin path. В DTO нет внутренних ID, прав, файловых ключей, персональных данных и upstream URLs. Продукт без eligible изображения получает null/пустой массив.

Браузерный `GET|HEAD /media/catalog/products/{slug}/{assetId}/{setId}/{variant}` направляется фиксированным Next handler к `/v2/public/catalog/products/{slug}/media/{assetId}/{setId}/{variant}` на конфигурируемом сервером NestJS origin. Никаких внешних redirects или пользовательских адресов. NestJS проверяет из одной короткой snapshot опубликованный активный товар, ревизию, права (включая expiry/revoke), exact set/variant и готовность. После snapshot читает и проверяет exact immutable bytes до заголовков, включая HEAD/304. Единственному открытому дескриптору нужна доказанная неизменяемость; при отсутствии гарантии использовать приватный bounded spool с проверенным digest либо закрывать выдачу. `404` для недоступной идентичности/версии/прав, `503` при отказе зависимости или нарушенной целостности. Успех `200 image/webp`, strong ETag по точным байтам, `nosniff`, без redirect и без byte ranges. Условный 304 только после всех проверок. Стартовый вариант cache policy — `Cache-Control: no-store` для изображений и media V2 payloads; любой cache TTL требует измерений и принятого окна отзыва. [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html).

Совместимость проверяется по неизменённым V1 маршрутам, payload/error golden fixtures, OpenAPI/client schema и permissions snapshot, включая legacy draft, publish/archive и клиентов без media. Проект name/ID grammar и размеры подлежат проверке на actual routing/proxy chain и измерениям.
