# R1-002 — авторизация, сессии, аудит и эксплуатационные границы

**Статус: PROPOSED. Версия: 0.1.0-proposed.** Все новые политики и числовые defaults ниже предложены для пакетного утверждения; они не приписываются прежним решениям владельца. ADR-003/001/004 и решения №16,49,50,55 сохраняются.

## 1. Границы доверия

Одна NestJS authority: локальные сотрудники, серверные PostgreSQL sessions, текущие permissions и object policy. Python/Next.js не принимают решения о правах. Health endpoints остаются public infrastructure. Staff API начинается `/v1/staff`; нет JWT, customer accounts, quote capabilities, IdP, MFA или UI входа в B. Собственные продавцы — записи одного внутреннего бизнеса, не tenants клиентов. GLOBAL доступ к их справочнику требует отдельного действия; доступ к будущим клиентским объектам этим не предоставляется.

Ответы staff API: `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`; requestId всегда новый серверный UUID, возвращается в `X-Request-Id` и `meta.requestId`/ошибке. Не доверять внешнему requestId как audit identity. Ошибки плоские: `{code,message,requestId,fields?}`; fields — только имя и машинный код без введённого значения. Не логировать тела входа, password/CSRF/session headers, Set-Cookie, hash, SQL bind parameters или произвольные exception details. Корреляция ошибки dependency — по requestId, без connection string.

## 2. Пароли и идентичность

- Email trim, ASCII max254, lower всей строки для уникальности C-collation; не удалять точки/+suffix. Формат OpenAPI нормативен; неизвестные поля DTO запрещены. В B email неизменяем, в том числе BLOCKED сохраняет уникальность.
- Пароль: 15..128 Unicode code points, UTF-8 <=512 bytes; без trim, Unicode normalization, требований к регистру/символам или молчаливого усечения. Не совпадает с emailNormalized; password/currentPassword — writeOnly. Не сохранять plaintext/обратимое шифрование. Проверка лимита bytes отдельно от JSON Schema maxLength.
- Argon2id PHC: рекомендуемые m=65536 KiB, t=3, p=1, salt=16 random bytes, hash=32 bytes. Принимаемые PHC параметры — контролируемый диапазон, не attacker-controlled huge allocation. Floor не ниже актуальной reviewed OWASP конфигурации; более слабый hash обновить при успешном login без изменения credentials/permission semantics, аудит `staff.password.rehashed` без PHC. Перед production benchmark на VDS; ориентир 250..1000ms, не утверждённый SLA. Максимум два параллельных hash verify на процесс, очередь16; переполнение ->503 DEPENDENCY_UNAVAILABLE, ограниченный таймаут ожидания2s.
- Для неизвестного/blocked пользователя выполнять dummy Argon2id того же профиля и общий bounded ответ. Неизвестный email, неправильный пароль, BLOCKED дают одинаковый 401 INVALID_CREDENTIALS и сообщение «Не удалось выполнить вход». Нет публичного поиска email/сброса/регистрации. Время не объявляется математически постоянным: проверяются отсутствие shortcut и сравнимое распределение, не flaky timing threshold.

Проверка currentPassword на PUT own-password имеет отдельный limiter ДО Argon: максимум10 всех попыток/15min/user,20/15min/source и5 неверных проверок/15min/user, backoff250ms..2s. HMAC keys не раскрывают user/source; counters атомарны Redis, успех сбрасывает только failure counter. Превышение ->429 RATE_LIMITED + Retry-After; Redis недоступен ->503, без verify/mutation. Глобальный Argon concurrency cap сохраняется и не заменяет эти лимиты. DENIED current password фиксируется как staff.password.changed с CURRENT_PASSWORD_INVALID без пароля.

## 3. Сессия

Token = 32 bytes CSPRNG, canonical base64url без padding (43 chars). Принимать ровно canonical43, иначе 401 AUTH_REQUIRED. В БД только SHA-256(raw 32 bytes), unique bytea32. Cookie — единственный транспорт; URL, JSON body/response, localStorage/sessionStorage запрещены. Новый login всегда новый token; блокировка/изменение прав/пароля не оживляет старые сессии.

Предлагаемые настройки:

| Параметр                          | Default           | Допустимость/обоснование                                                   |
| --------------------------------- | ----------------- | -------------------------------------------------------------------------- |
| absolute expiry                   | 12 часов          | 1..24h, не продлевается активностью; одна рабочая смена                    |
| idle expiry                       | 30 минут          | 1..120min и <= absolute; ограничение оставленной рабочей станции           |
| max active sessions/user          | 5                 | 1..10; при новом login отозвать самые старые по createdAt/id транзакционно |
| login challenge TTL               | 10 минут          | 1..15min; Redis ephemeral, не job                                          |
| failed-login source               | 30 / 10min        | источник IP после trusted-proxy validation                                 |
| failed-login normalized account   | 10 / 10min        | тот же HMAC key для известных/неизвестных учёток                           |
| failed-login pair                 | 5 / 5min          | источник + account; ограничение распределённого/локального перебора        |
| all login attempts source ceiling | 60 / 10min        | до Argon и создания дорогого аудита; успех не обходит лимит                |
| preauth CSRF issuance             | 60 / 10min/source | предотвращение бесконечного Redis state                                    |
| generic failure backoff           | 250ms..2s         | bounded, без долгого account lock и вечных таймеров                        |

Limits используют атомарные Redis counters/TTL и HMAC-SHA256(account/source) с отдельным server RATE_LIMIT_KEY >=32 random bytes; raw email/IP не часть Redis key/log. Успешный login сбрасывает account/pair failure counters, не source ceiling. 429 RATE_LIMITED с целым Retry-After; правила одинаковы для всех существующих/несуществующих account. Redis недоступен: preauth/login/own-password ->503, не fail-open. В B Redis не хранит ни authority sessions, ни jobs. Критические auth/audit DB сбои ->503; доступ через старый positive cache запрещён. Rate limiter endpoint-ов login и own-password применяется до lookup account. Дополнительный perimeter limit конфигурируется у proxy, не заменяет серверный.

Проверка каждой сессии: tokenHash -> StaffSession -> StaffUser ACTIVE, authVersion равен текущему, revokedAt NULL, `now < absoluteExpiresAt`, `now < lastSeenAt + idleTimeoutSeconds`. Равенство deadline означает expiry. Временная authority для expiry/revocation/activity — свежий PostgreSQL `clock_timestamp()`, взятый ПОСЛЕ соответствующих row-lock waits; не `now()`/`CURRENT_TIMESTAMP`/`transaction_timestamp()`, которые фиксируют начало transaction. Сравнение deadline и lastSeenAt используют этот свежий момент, не browser clock. createdAt/occurredAt могут иметь transaction timestamp для истории, это не authority истечения. При успешном запросе lastSeenAt обновляется до DB now, без продления absolute. UPDATE содержит повторные predicate revoked/expiry/authVersion/ACTIVE; после ожидания row-lock не обновлять уже отозванную сессию. Нет Redis permission cache. Cookie Max-Age не длиннее absolute, серверные сроки главнее cookie.

`passwordChangeRequired=true`: разрешены только me, me/permissions (пустой permissions), CSRF, logout, собственная смена пароля; прочее ->403 PASSWORD_CHANGE_REQUIRED до обычных permission checks. Самостоятельная смена требует currentPassword, не только действующего cookie. В одной транзакции изменить hash, снять flag, увеличить authVersion/version, revoke все старые sessions, создать новую с новым token и аудит; Set-Cookie отправляется после commit. Повтор/неоднозначный transport failure не переиспользует старый token; новый login. Пароль меняется без дополнительных admin прав.

На admin security mutations используется lock/порядок из RBAC; сохраняется пригодный ACTIVE full-admin с собственным union всех 12 явно зафиксированных fullAdminProtectedPermissions одновременно с control-admin. READ COMMITTED, advisory lock до чтения состояния, пересчёт результирующего union перед commit; block/role unassign/role permissions/state/password readiness и прочие влияющие writers не обходят проверку. Роли configurable, self-edit/default deny/grant ceiling сохраняются. На LAST_ADMIN_REQUIRED бизнес-строки, версии и сессии rollback, SUCCESS audit отсутствует, отдельный обязательный DENIED audit; его сбой503. Нет privileged bypass. Будущие permissions не включаются автоматически; authorization повторяется внутри транзакции после advisory lock. Бизнес-write после guard удерживает shared actor StaffUser/session row locks до commit; invalidation writers берут конфликтующие locks. В каждой ветке один порядок: advisory (если нужен), StaffUser UUID sorted, Role UUID sorted, StaffSession UUID sorted. Уже авторизованный read может закончиться параллельно revoke; запрос после завершённого revoke обязан получить 401. Нельзя принимать финансовое/инженерное решение в будущем по устаревшему auth snapshot. B проверяет гонки status/permissions/session revoke с реальным PostgreSQL, не только mocks.

## 4. Cookie, Origin, CSRF, CORS

| Среда                   | Staff cookie        | Login challenge cookie | Flags / origin                                                                                                                                                  |
| ----------------------- | ------------------- | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| HTTPS production        | `__Host-stdu_staff` | `__Host-stdu_login`    | HttpOnly; Secure; SameSite=Lax; Path=/; **без Domain**. Один PUBLIC_WEB_ORIGIN из конфигурации, API по тому же HTTPS origin через reverse proxy                 |
| Явный local development | `stdu_staff_dev`    | `stdu_login_dev`       | HttpOnly; Secure=false; SameSite=Lax; Path=/; без Domain. Только loopback 127.0.0.1 и APP_ENV=development; web http://127.0.0.1:3000, API http://127.0.0.1:3001 |

Dev cookie не изолирована по порту: оба loopback-приложения считаются одной доверенной границей; Next не пишет Cookie headers в logs. Не смешивать localhost и 127.0.0.1. HTTP/no-Secure вне loopback development — startup configuration error. Production без заданного HTTPS origin/key не стартует staff auth; домен/ключи не выдумывать. Proxy сохраняет Host/Origin и X-Forwarded-Proto; доверять X-Forwarded-* только от одного явно настроенного proxy hop/private network, backend не доступен напрямую из интернета. Нельзя trust proxy=true для произвольных источников.

Dev browser fetch: API URL3001, `credentials:'include'`; allowed Origin **ровно** http://127.0.0.1:3000, Access-Control-Allow-Credentials=true, Vary: Origin. Никакого wildcard/reflection/suffix matching. Allowed methods GET/POST/PUT/PATCH/DELETE/OPTIONS; headers Content-Type, X-CSRF-Token; expose X-Request-Id и Retry-After. Production CORS cross-origin отключён, разрешён один same public origin. Preflight без auth возвращает204 только для точного разрешённого origin/method/header; не даёт бизнес-доступа. CORS headers не заменяют Origin/CSRF проверку. GET с присутствующим чужим Origin также отклоняется; допустимый GET без Origin не обходится в unsafe операции.

Все POST/PUT/PATCH/DELETE: require exact configured Origin, reject absent/null/untrusted ->403 ORIGIN_FORBIDDEN. Require X-CSRF-Token ->403 CSRF_INVALID. Content-Type application/json для тела, другие ->415 UNSUPPORTED_MEDIA_TYPE. Sec-Fetch-Site=cross-site отклонить; same-site сам по себе не разрешает origin. Не полагаться только на SameSite, Referer или CORS. Защищённый маршрут сначала проверяет сессию (401), затем Origin/CSRF (403), затем password-change policy/permission/object.

CSRF — session-bound HMAC, **не staff credential**. CSRF_KEY >=32 random bytes, отдельно от RATE_LIMIT_KEY; raw key никогда не DTO/БД. `base64url(HMAC-SHA256(CSRF_KEY, UTF8(purpose + '\0' + binding)))`, где purpose строго `staff-csrf-v1` или `login-csrf-v1`; binding для staff = session.id + '\0' + hex(tokenHash), для login = hex(SHA256(raw challenge)). Полный input server-only, token —43 chars. Constant-time equal decoded32 bytes; строгое canonical encoding/length. Стабилен до конца текущей session/challenge, поэтому разные вкладки не инвалидируют его GET-запросом. Key rotation инвалидирует CSRF; клиент повторяет GET csrf. Не передавать session id/hash в CSRF token. Изменение токена staff session автоматически меняет CSRF binding.

Порядок login:

1. GET `/auth/csrf`: валидная staff session -> JSON `{token,context:'STAFF'}`; иначе создать/переиспользовать неистёкший random32 login challenge, в Redis только key SHA256(challenge)+TTL, выдать HttpOnly challenge cookie и JSON HMAC token/context LOGIN. Ответ no-store; expired staff cookie очистить. JS хранит CSRF только в памяти.
2. POST `/auth/login` требует Origin и challenge CSRF до lookup/password; atomic consume Redis challenge (GETDEL/Lua) единожды. Невалидный challenge ->403 CSRF_INVALID. После неудачного входа получить новый challenge; никакой auto endless retry.
3. Valid staff session при повторном login ->409 ALREADY_AUTHENTICATED после проверки её staff CSRF, переключение через logout. Argon verification вне короткой transaction запоминает **точные passwordHash и authVersion**, по которым пароль проверен. Затем transaction берёт StaffUser row FOR UPDATE до любых session locks и повторно проверяет ACTIVE, совпадение обоих snapshot values и актуальный профиль. Изменившийся hash/authVersion (включая recovery, password change, block/permission change) -> тот же generic401 INVALID_CREDENTIALS, без новой сессии/Set-Cookie. Нельзя выдать current-version сессию по паролю, проверенному до такого изменения. Под тем же user lock подсчитать неистёкшие/неотозванные sessions, отозвать самые старые сверх лимита с учётом новой, создать session и SUCCESS audit. Это сериализует конкурентные login одного пользователя и max-session limit. Только после commit Set-Cookie staff, очистить challenge cookie; JSON содержит Me, **не auth token**. Затем GET csrf для STAFF контекста. Rehash и собственная смена пароля тоже сравнивают credential snapshot под тем же lock; проигравшая гонку проверка не перезаписывает новый пароль.
4. POST `/auth/logout` требует валидную session+Origin+staff CSRF, revoke +audit одной транзакцией; очистить cookie с теми же path/flags, Max-Age=0. У неизвестной/expired/revoked session ->401 AUTH_REQUIRED с очисткой cookie. Audit failure ->503, session и cookie сохраняются, retry безопасен.

CSRF token — единственное специально разрешённое некреденциальное secret-поле ответа; оно не даёт входа без HttpOnly cookie. Все тесты «no secrets in DTO/log» запрещают password/PHC/session token/hash/key/cookie, но не удаляют необходимый CSRF ответ; CSRF всё равно не логируется. Защита от XSS и untrusted same-origin script необходима, CSRF не защищает украденный origin.

## 5. Bootstrap и recovery — только явные операторские команды B

Имена команд ниже — **планируемые**, сейчас их не существует. Нет account/пароля по умолчанию, env seed пользователя, публичной reset-формы или autostart bootstrap.

- `pnpm --filter @stdu/api staff:bootstrap --email <owner-email> --display-name <name> --operator <label>`: оператор с авторизованным shell доступом на local/VDS. Обязательный display-name: trim, 1..120 code points, те же правила DTO/DB; имя не выводится автоматически из email. Пароль дважды в скрытом TTY prompt; для автоматизированного одноразового теста только защищённый stdin pipe/secret mount, никогда argv/env/log/Git. Ограничить secret file ACL/0600 и не делать transcript. Хэш рассчитывается до короткой DB transaction; затем общий advisory lock, StaffUser count **0** (не «нет admin», не «все blocked»), insert ACTIVE passwordChangeRequired=false + обычная bootstrap-admin роль assignment, пересчитать оба инварианта (все 12 защищённых действий) + OPERATOR audit, commit; вывести только id/email и успешный факт. Никакая сессия не создаётся. Два параллельных bootstrap: ровно один проходит, второй409 BOOTSTRAP_ALREADY_COMPLETED, атомарно без половинчатого admin. Уже существующую seed роль не пересоздавать/не расширять автоматически.
- Admin POST users передаёт initialPassword writeOnly >=15 с политикой выше; создаёт ACTIVE passwordChangeRequired=true **без ролей**. Ответ не повторяет пароль; ручная передача сотруднику вне логов/платформы — ответственность оператора/администратора. Роли выдаются отдельным действием. До смены initial password опасные действия запрещены. Это предложенный минимальный процесс без email/reset инфраструктуры, подлежит утверждению владельцем.
- `pnpm --filter @stdu/api staff:recover --user-id <uuid> --operator <label> --reason OWNER_CONFIRMED`: только доверенный операторский shell после подтверждения личности владельцем вне приложения; пароль скрыто дважды. ACTIVE пользователь должен существовать, роли не меняются, BLOCKED не разблокируется. Lock и повторная проверка состояния, новый hash, passwordChangeRequired=true, authVersion/version++, все sessions revoked, OPERATOR audit атомарно. Под тем же lock проверить результат установки required flag: если исчезает последний пригодный control-admin ИЛИ full-admin (даже когда другой access-admin остаётся), **не ставить required flag**; восстановленный секрет устанавливается самим владельцем через доверенный канал. Эта ветка требует явный `--last-admin-owner` и повторное операторское подтверждение; без него409 LAST_ADMIN_REQUIRED, никаких изменений. В этом случае отдельный audited `recoveryMode=LAST_ADMIN_OWNER`, вывод без секрета; оба набора permissions и роли не меняются, оба инварианта проверяются перед commit; этот режим сохраняет пригодность credentials, не освобождает от проверки. Если целевой пользователь уже passwordChangeRequired=true, его pending secret нельзя объявить owner-ready этим флагом: требуется штатная own-password смена; если исходный full-admin инвариант уже нарушен, STOP без commit и отдельный согласованный recovery plan. Потеря прав из-за прямого аварийного SQL не «исправляется» этим CLI: отдельный согласованный recovery plan, без silent bootstrap повторно.
- OPERATOR actor не staff impersonation. operatorLabel — заявленная оператором метка, requestId — новый UUID invocation; связь с shell/VDS audit вне приложения, не криптографическое доказательство личности. CLI не доступен через HTTP и не исполняет пользовательские команды. Использует тот же transactional application service/runtime DB role и проверки. Production выполнение требует отдельной операции владельца, merge кода его не запускает.

## 6. Аудит и сбои

Нормативный machine-readable action/reason/changes registry: [R1-002-audit-registry.json](R1-002-audit-registry.json). SUCCESS с null reason разрешён только там, где явно указан null в registry; DENIED/FAILURE всегда имеет код. CLI recovery принимает только OWNER_CONFIRMED; LAST_ADMIN_OWNER — отдельный audited changes.recoveryMode, не произвольная строка причины. StaffSession.revocationReason тоже только из sessionRevocationReasons registry. Action/reason/outcome/root changes keys проверяются PostgreSQL immutable validation function (CASE-константы из registry) + CHECK, а не запросом к другим таблицам; типы значений валидируются как закрытый AuditChanges DTO. Старые допустимые action/reason не удаляются при последующем расширении истории.

Краткая карта действий:

| Действие                        | Audit action                                                                                | Данные changes (только allowlist)                                                                                 |
| ------------------------------- | ------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| login success/failure/limit     | auth.login                                                                                  | outcome; reasonCode; affected user id только если разрешено внутреннему audit; account HMAC fingerprint без email |
| logout                          | auth.logout                                                                                 | session opaque internal id в entityId, reasonCode                                                                 |
| revoke/rotation/expiry observed | staff.sessions.revoked / auth.session.rotated / auth.session.expired                        | target user id, count, reasonCode; без session hashes/tokens                                                      |
| bootstrap/recover/password      | staff.bootstrap / staff.access.recovered / staff.password.changed / staff.password.rehashed | target user id; required flag; recoveryMode; без password/PHC                                                     |
| create/block/unblock            | staff.user.created / staff.user.state.changed                                               | changed field names; state old/new; без email/initial secret                                                      |
| role create/rename/archive      | staff.role.created / staff.role.changed                                                     | role id, changed field names, state old/new                                                                       |
| assignment add/remove           | staff.role.assigned / staff.role.removed                                                    | target user id, role id                                                                                           |
| replace role permission set     | staff.role.permissions.changed                                                              | role id, added/removed permission codes, affected user count                                                      |
| seller create/edit/state        | seller.created / seller.changed                                                             | seller id, changed field names/state old/new; без полных реквизитов                                               |
| file metadata commands later    | file.metadata.changed / file.version.created / file.link.changed                            | ids, version number, field names; НЕ реализуются B                                                                |

Handler-level auth/administrative failures -> same action + DENIED/FAILURE и bounded reasonCode. Обязательный DENIED AuditEvent относится к выполненной credential check и к административной команде после прохождения transport/auth guard: сюда входит бизнес-валидация нового пароля/reuse с VALIDATION_ERROR и повторный login с ALREADY_AUTHENTICATED. Pre-handler malformed JSON/DTO/415, missing-session401, Origin/CSRF reject и rate rejection до credential/command check не создают AuditEvent на каждый запрос: только bounded source counters/технические метрики, без body/PII. Registry разрешает соответствующие коды для контролируемой диагностической записи, но B не обещает и не делает per-request INSERT на flood. Read-only GET не создаёт административный audit изменения. Все реально записываемые action/outcome/reason соответствуют finite registry; unknown auth target entityType/id оба NULL, actor ANONYMOUS, requestId обязателен. Login account fingerprint/sourceHash — HMAC, не raw email/IP; это всё ещё чувствительные служебные данные. Аудит читается только audit.read, без произвольного payload export. Анонимные 401 от любого сканируемого staff GET не создают бесконечный audit row; auth login failures агрегируются rate gate/максимальными лимитами, 429 до account lookup записывается source-only в bounded счётчик/техническую метрику, без бесконечного INSERT на каждый flood. Успешные и допущенные к credential check неуспешные login фиксируются обязательно; limit rejection не называется успешным audit insert.

SUCCESS административной мутации, invalidate sessions и AuditEvent — **одна PostgreSQL transaction**. Audit INSERT failure: rollback mutation/revocation, ответ503 AUDIT_UNAVAILABLE, никакого PASS/204/Set-Cookie; error log только requestId и код. Login success не выдаёт сессию без зафиксированного SUCCESS audit. Failed-login аудит пишется отдельной короткой transaction: не записался ->503 AUDIT_UNAVAILABLE одинаково для неизвестного/известного. DENIED admin mutation: rollback бизнес-транзакции, отдельная audit transaction, при её сбое ->503; права не появились. При read audit outage не использовать cache;503.

Audit append-only обеспечивается PostgreSQL grants+trigger для runtime identity; migration owner/DB superuser остаётся доверенной операционной границей. Actor FK RESTRICT: блокировка сотрудника не удаляет историю. Ретенция/обезличивание PII требует решения владельца до production, автоматического purge в B нет. Нет outbox/брокера/усиленного enterprise-аудита на этом шаге: локальная транзакционная таблица достаточна для этих синхронных операций.

## 7. Проверяемая поверхность и источники

Точные DTO/errors/permissions/CSRF/audit и validation — [OpenAPI](R1-002-staff.openapi.json). Матрица RBAC и PostgreSQL integrity — отдельные файлы, тестовая трассировка — [test matrix](R1-002-test-matrix.md). Все проверки runtime остаются NOT IMPLEMENTED до B.

Основания технических рекомендаций: [OWASP sessions](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html), [OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html). Значения конфигурации/локальный протокол/HMAC binding и административные ограничения выше — предложения этого контракта, не утверждение, что OWASP задаёт именно их.
