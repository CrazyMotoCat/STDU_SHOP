## Source and compatibility

This contract covers REQ-01…04, CAT-01, CAT-03, CAT-07, R1-010 in the backlog, and REQB-01…41. It extends but does not amend FROZEN R1-002, R1-004, R1-006A or R1-007A, nor decisions 1–108. It uses the R1-010A proposal in PR #18 as read-only input. The compatibility matrix is recorded in the review report; the front-end proposal remains preview-only, owned by its author and is not edited here.

The application remains the existing modular monolith: Next.js calls NestJS; NestJS owns Inquiry authorization, validation, transactions and audit; PostgreSQL is the business source of truth; Redis backs bounded anti-abuse counters; the configured private StoragePort stores original bytes. R1-010 does not call FastAPI. Customer document parsing is R1-011.

## Scope

One Inquiry aggregate supports EQUIPMENT, PANELS and ENGINEERING requests. It preserves submitted wording and equipment lines, records a contact snapshot, accepts privately quarantined originals, and exposes a permission-scoped staff queue, assignments, transitions, history, internal comments and protected document access. Staff actions are individually authorized, audited, idempotent and use OCC where they mutate aggregate state.

The frozen model defines six tables: Inquiry, InquiryLine, InquiryComment, InquirySourceDocument, InquiryUploadIntent and InquiryCommandIdempotency. AuditEvent and StaffUser are reused; a product context hint and per-line product slug are stored only as untrusted text, with no catalog FK or lookup. Each Inquiry captures the server-selected immutable upload-profile code. There are 15 OpenAPI operations (4 public and 11 staff) and 9 additive permissions. The staff API exposes an optional human-managed due date for the current workflow stage, distinct from the customer's desired deadline; there is no automatic SLA calculation or notification. See the data model, OpenAPI, upload profiles, RBAC matrix, audit registry and acceptance matrix for normative details.

## Non-goals

No customer account, public inquiry lookup/status API, order, BOM, cost calculation, quote generation, automatic SKU match, substitute selection, bulk approval, PDF/XLSX/CSV extraction, OCR, supplier import, automatic permission grant, notification provider, production migration or deployment. QUOTE_SENT is set only by a later quote-delivery command; it cannot be forged through a generic staff transition. R1-010 does not add native CAD or archive support and cannot complete document-led work while no scanner is operational.

## Request shapes

- EQUIPMENT requires one to 50 separate InquiryLine entries. Each line retains raw title, original SKU, manufacturer, modification, quantity string, unit and comment. An optional request-level `catalogProductContext` and optional per-line product slug are untrusted context only; neither is resolved, matched or linked automatically.
- PANELS requires PROJECT_READY, MODIFY_TYPICAL or DEVELOP_FROM_BRIEF and a non-empty task/description. Cabinet purpose and positive quantity are optional; free-text requirements, selected work/services, documentation availability and notes are preserved when supplied. The three identifiers align with the read-only R1-010A proposal.
- ENGINEERING requires only a non-empty technical task/subject. Direction/service area, system/object, expected outcomes, source-document description, scope and notes are optional bounded text and are preserved when supplied.
- Contact name is required; at least email or phone is required in the recommended model. Organization, tax identifier, preferred channel, region, verbatim desired-deadline wording and customer comment are optional. The desired deadline is not parsed into a date, SLA or stage due date. Exact legal notice/consent is unresolved in OD-010-02.

All user text is inert, bounded and escaped on display. Unknown fields are rejected. The initial customer submission, equipment lines, kind and public receipt are immutable snapshots. Staff cannot rewrite what the customer submitted; corrections are added as internal comments or future explicitly versioned records.

## HTTP semantics

POST /v1/public/inquiries creates synchronously. It returns 201 only after the Inquiry, lines, durable idempotency result and inquiry.created audit commit in one PostgreSQL transaction. The receipt contains a random opaque publicReference, timestamp and a neutral acknowledgement with no response-time promise. The reference provides no query or file access. OD-010-05 preliminarily accepts 201; a 202 response would require a separately approved asynchronous-acceptance design and is not part of this proposal.

Every mutating command requires Idempotency-Key. The key is hashed, request hashes use RFC 8785 canonical JSON of validated normalized input, and the response receipt is persisted in the same transaction. Create-request canonicalization includes SHA-256(uploadCapability), never the raw capability. Upload-content canonicalization includes the actual byte digest, detected MIME, byte count and bound intent ID. Same key and same hash replays exactly; same key with another hash returns 409 IDEMPOTENCY_KEY_REUSED. PostgreSQL unique indexes serialize concurrent requests. Before a staff receipt is looked up or replayed, the API revalidates the live session, CSRF/Origin, action permission and read scope for the Inquiry; before upload receipt replay, it revalidates the current unexpired capability and bound intent. Authorization failure returns no stored receipt. Public create replay returns only the non-authorizing original receipt. Retention is 30 days; clients must generate a fresh unpredictable key for every new action and never reuse an expired key. Request bodies and capability values are never stored in idempotency records.

Staff aggregate changes require If-Match with the Inquiry version. The version predicate, row update, transition/assignment/stage-deadline audit and idempotency receipt commit atomically. A stale request returns and durably replays 409 VERSION_CONFLICT without partial mutation or success audit. Assignment commands assign or replace an ACTIVE staff member; clearing is not supported. `TransitionRequest` is a disjoint union: ordinary workflow transitions cannot set QUOTE_SENT/CLOSED; a strict pre-quote closure variant can set CLOSED only from NEW, TRIAGE, NEEDS_CLARIFICATION, ENGINEERING_REVIEW or READY_FOR_QUOTE and only with reasonCode DUPLICATE, CUSTOMER_WITHDRAWN, OUT_OF_SCOPE, SPAM or NOT_FEASIBLE. It uses `inquiries.transition`, current read scope, If-Match and Idempotency-Key; the state change, stageDueAt clear, version increment, `inquiry.closed_without_quote` AuditEvent and receipt commit atomically. The original submission remains immutable, no quote/order is created, and CLOSED cannot be reopened. A closed Inquiry remains visible in authorized staff history/detail. QUOTE_SENT still requires a corresponding approved and sent immutable quote revision; only its later quote lifecycle may set CLOSED. A successful status transition clears the optional staff-managed `stageDueAt`; it can then be set or cleared explicitly with If-Match, audit and idempotency. Comments are append-only and independently idempotent; concurrent comments cannot overwrite each other.

## File boundary

The public client generates a 256-bit CSPRNG upload capability when an attachment is selected. The initial create request carries it only in the JSON `uploadCapability` field; later intent, upload and cancel requests carry it only in `X-Inquiry-Upload-Capability` on the capability-only routes defined by Contract Amendment 01. The server resolves the active Inquiry from the unique SHA-256 hash and checks that the intent belongs to it. Inquiry creation stores only the hash, with a recommended 24-hour expiry; no response contains the secret. That capability is accepted only for creating/uploading/cancelling intents bound to the same Inquiry. It never authorizes reading Inquiry data, status, attachment metadata or bytes. An optional request-level `catalogProductContext` is preserved only as an untrusted hint and never grants catalog access or links a product. Each Inquiry captures a server-selected immutable upload profile; each intent binds one file, declared name/type/size and start expiry and may be consumed once. An active stream receives the profile's separate 15- or 60-minute deadline and remains quota-reserved until it completes, fails or expires. Knowing an Inquiry or intent UUID is insufficient.

The file is streamed through NestJS into an opaque private quarantine key, bounded while reading, sniffed against the approved allowlist and hashed. A completed attachment is a separate immutable InquirySourceDocument. It is never stored as a staff-owned R1-002 FileObject or linked through generic FileLink: those frozen tables require staff ownership. Only the existing private StoragePort implementation is reusable. There are no static or public object URLs. Incomplete temporary bytes are removed after 24 hours by ownership-checked cleanup. A failed attachment does not roll back the Inquiry or prior attachments.

New public files start QUARANTINED. Only the configured malware-scanner integration may move a file to CLEAN or REJECTED. Without an operational scanner, the contract fails closed: files remain unavailable for download and R1-011 extraction. Structural MIME checks are not a malware verdict. Download requires inquiry visibility plus both document permissions and CLEAN state, streams through NestJS with no-store/nosniff and attachment disposition, and never returns storage keys. OD-010-03 proposes MVP_SAFE as the default (10 MiB/file, five files, 25 MiB/Inquiry, 100 MiB/source/day) and an opt-in ENGINEERING_DOCUMENTS profile (50 MiB/file, 20 files, 250 MiB/Inquiry, 1 GiB/source/day). Both allow only PDF/CSV/XLSX. Without a real scanner, neither profile permits staff download. DOCX, DWG/DXF and archives remain excluded pending separate content-validation and safe-handling review.

## Anti-abuse and privacy defaults

The frozen upload profiles in `R1-010-inquiry-upload-profiles.json` are server-side configuration and cannot be selected by anonymous clients. They share create limits of 5/15 minutes and 20/day per source, 2 MiB create JSON, 50 equipment lines and 30-minute intent start expiry. MVP_SAFE uses 10 upload intents/hour and 100 MiB/day declared bytes/source, five files and 25 MiB completed bytes/Inquiry, 10 MiB/file and a 15-minute active-stream deadline. ENGINEERING_DOCUMENTS uses 40 intents/hour and 1 GiB/day/source, 20 files and 250 MiB/Inquiry, 50 MiB/file and a 60-minute deadline. Both use atomically charged declared bytes and no refund for failed/cancelled/expired intents during that day; profile caps cannot widen an already charged source/day bucket. Existing Redis counters reuse R1-002 `RATE_LIMIT_KEY` with an Inquiry-specific HMAC namespace and no new secret. Trust forwarded source headers only from the explicitly configured reverse proxy hop; otherwise use the direct peer. Never trust arbitrary X-Forwarded-For. If Redis or required private storage is unavailable, reject public writes with a safe 503.

Require exact configured Origin on public browser writes and disable credentialed wildcard CORS. Public writes do not use cookies, so no ambient browser authority is granted. Staff writes follow the exact FROZEN R1-002 session-cookie, CSRF and Origin policy. Logs, traces and AuditEvent exclude request bodies, PII, raw IP, capability, filenames, file bytes, comments, storage keys and exception payloads. Public errors do not reveal Inquiry existence or internal dependency details.

The exact legal basis, text/checkbox, consent evidence, retention/deletion and commercial launch gate are not inferred; they require OD-010-02 and legal review. No production collection is authorized by this proposal.
