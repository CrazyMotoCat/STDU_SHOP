# Протокол оркестрации Codex — пользователь руководит, код пишут ИИ-агенты

## Роли

- **Пользователь / продуктовый владелец / оркестратор:** утверждает требования, объём, приоритеты, архитектурные решения и критерии приёмки; ревьюит UX и принимает функциональный результат/релизы. Безопасные push/merge ведущего агента не требуют отдельного подтверждения по каждому PR. Не обязан самостоятельно писать код.
- **Ведущий агент-интегратор:** читает ТЗ, предлагает ADR, владеет миграциями/доменными контрактами и интеграцией PR, следит за единством проекта, держит backlog и риски.
- **Агенты-исполнители:** получают маленькую область кода; frontend, backend, parser, QA, infra — роли по потребности, не постоянные запущенные процессы.
- **Агент-ревьюер:** проверяет ограничения решений, тесты, утечки внутренней информации, пересечения контуров и качество диффа; не переписывает архитектуру без запроса.

## Основные правила

1. Для каждой задачи указывать Task-ID, scope, non-goals, входные DTO, выходные файлы, тесты, критерии приёмки.
2. Ведущий агент **первым** фиксирует общий контракт (миграция + OpenAPI + auth model) и только затем выдаёт независимые реализации.
3. Не более 2–3 параллельных write-агентов на начальных итерациях; увеличивать только при устойчивом CI и минимуме merge-конфликтов. Это инженерная рекомендация, а не гарантия лимитов подписки.
4. Исключительные права на общую схему БД/миграции, OpenAPI, RBAC и общие библиотечные типы принадлежат одному агенту на итерацию. Остальные работают по утверждённому контракту.
5. Независимые параллельные write-агенты работают в отдельных ветках/worktree. Единственный ведущий writer может работать в main по DIRECT_MAIN; отдельная ветка на каждую задачу не обязательна. Интеграция только после применимых проверок/ревью. Контракты и документы версионируются вместе с кодом.
6. Каждое изменение принятого решения №1–108 требует явного пользовательского согласования и обновления реестра. Агент может предложить ADR реализации, но не отменить бизнес-ограничение.
7. Не генерировать большие неиспользуемые модули «на будущее». Заложить устойчивые ключи, ports/interfaces и миграции для расширения.
8. Если задача внезапно превышает scope, агент останавливает расширение и предлагает отдельный Task-ID.
9. Ревьюер проверяет фактический вывод команд; фразы «тесты прошли» без выполненного прогона не принимаются.
10. CI, security и восстановление бэкапа — обязательный этап перед любой продовой поставкой, даже при полностью ИИ-разработке.

## Выбор режима и автономная интеграция

Постоянное разрешение владельца на коммиты, push и merge и полные условия трёх режимов зафиксированы в [Git Delivery Policy](../../AGENTS.md#git-delivery-policy). В начале задачи ведущий агент выбирает режим по риску; явное указание владельца имеет приоритет в пределах безопасности и правил GitHub. При неопределённости выбирается более безопасный режим.

- **DIRECT_MAIN:** ограниченные изменения низкого риска. Сначала свежий fetch, синхронизированная main, чистые/известные изменения, единственный writer, отсутствие изменений миграций/RBAC/session security/финансов/критических доменных правил. После локальных проверок и secret/diff review — коммит, повторная проверка origin/main, обычный push и успешный CI точного SHA. Запрет прямого push в GitHub переводит доставку в AUTO_MERGE без обхода защиты.
- **AUTO_MERGE (по умолчанию для функций):** актуальная main → короткоживущая ветка → scope/контракт → реализация и тесты → PR → успешные обязательные checks актуального HEAD/merge-кандидата → самостоятельный merge → подтверждение интеграции и обновление локальной main/checkpoint. Не должно быть конфликтов, блокирующих замечаний, запрещающих интеграцию unresolved threads или запрета владельца. Обязательные approvals и branch protection соблюдаются. При высоком риске требуется независимое read-only review; HIGH/BLOCKER запрещает merge.
- **REVIEW_REQUIRED:** новые/изменённые бизнес-правила, существенные ADR/архитектура/scope, несогласованные контракты, потеря данных/необратимые миграции, рискованные production-операции и production-секреты требуют решения владельца. Безопасная подготовка возможна; опасная операция или требующий решения merge блокируются до согласования.

RBAC/API/БД по уже утверждённому контракту допускают AUTO_MERGE после применимых security-тестов и независимого ревью при высоком риске. Сам merge не разрешает production-миграции. Ручные бизнес-согласования остаются обязательными. При невозможности интеграции сообщать точный blocker; готовый локальный код или PR не означают полную доставку.

## Когда выдавать субагентам работу

- Подходят: UI реализации на зафиксированном API, unit/E2E suite, parser fixture adapters, независимые страницы и документация.
- Не подходят: одновременно схема каталога и миграции, разные понимания формулы цены, редакции КП и auth, параллельные правки одних и тех же DTO.
- На каждое задание отдавать только релевантный контекст из `03_MASTER_TZ_R1.md` и инварианты из `05_DOMAIN_MODEL.md`, не весь чат.

## Процесс разработки одной функции

```text
1. ORCHESTRATOR: выбрать Task-ID и зафиксировать критерии.
2. LEAD: выбрать Delivery Mode по риску, проверить зависимые миграции/ADR/API, создать короткий план.
3. WORKER: реализовать в своём scope + тесты + changelog.
4. REVIEWER: проверить решения, безопасность, regression и diff.
5. LEAD: выполнить применимые проверки и доставить по выбранному режиму; в AUTO_MERGE самостоятельно объединить прошедший все условия PR, проверить интеграцию и итоговый main SHA.
6. ORCHESTRATOR: принять функциональную демонстрацию или вернуть замечания; отдельно решить только вопросы REVIEW_REQUIRED.
7. LEAD: обновить checkpoint/статус, таблицу трассировки и backlog.
```

## Шаблон запроса ведущему агенту

«Выполни `R1-004`. Перед кодом прочитай `AGENTS.md`, `docs/spec/02_RELEASE_SCOPE.md`, `03_MASTER_TZ_R1.md`, `04_ARCHITECTURE.md`, `05_DOMAIN_MODEL.md`. Укажи затрагиваемые доменные инварианты и контракты. Не реализуй склад, закупочные заказы или автоматические аналоги. Раздели реализацию на небольшие PR. Приведи команды реально выполненных проверок и докажи результат через тесты».

## Итоги каждой сессии Codex

Каждый агент возвращает по схеме: Task-ID, Delivery Mode, выполнено, основные файлы, фактически выполненные проверки, CI, ссылка на PR при наличии, статус PUSHED/MERGED/BLOCKED, итоговый main SHA при доставке, ограничения и следующий узкий шаг. DIRECT_MAIN завершён после push в main и успешного CI; AUTO_MERGE — после merge и подтверждения интеграции; REVIEW_REQUIRED — подготовка к решению владельца с сохранением блокировки опасных операций. Пользователь должен быть способен продолжить проект с новым агентом, не читая полный лог предыдущей сессии.
