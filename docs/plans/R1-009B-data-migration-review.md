# R1-009B data and rollout review

**DRAFT / REVIEW_REQUIRED / NOT FROZEN**

| Option                         | Consequences                                                                                                                                                                                                                                                         |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. Extend IngestionApplication | Retains global UNIQUE(row_id), UNIQUE(decision_id) and UNIQUE(revision_id) for old and new writers. Add operation discriminator and nullable base revision. Prisma changes one relation to optional. Existing IDs and history remain intact.                         |
| B. Separate CREATE provenance  | Keeps current UPDATE schema intact, but separate UNIQUE constraints cannot guard CREATE versus UPDATE. Requires a shared claim table or coordinated triggers and an extra lookup. All old and new paths would need to claim the same row. Reporting becomes a union. |

Recommend A. Add operation with default UPDATE and restrict to UPDATE or CREATE. Historical rows remain UPDATE with their base revision intact. CHECK requires UPDATE base revision present and distinct from result, version greater than 1. CREATE requires base revision absent and version 1. Use composite FKs from (baseRevisionId, offerId) and (revisionId, offerId) to the existing unique revision pair, with ordinary nullable FK behavior only for the absent CREATE base. Keep independent offer FK and existing row/decision/revision uniqueness. Retain append-only ownership, trigger and runtime SELECT/INSERT grants.

Validate relationships under transaction locks: accepted decision names row, row belongs to run, run source and captured revision/hash match, supplier matches source, offer and supplier active, source enabled/current, result revision belongs to offer and author matches employee. UPDATE must advance from its genuine base. CREATE must point at the newly inserted revision 1 with no catalog match upon insertion. Use the existing deferred offer/current-revision relationship for root and revision creation. Keep historical UPDATE audit and record operation, change field names, actor, application and revision references in additive restricted audit as needed. Never include evidence text or supplier facts in generic audit.

Rollout: inspect real constraints, existing data and triggers; validate historical composite relationships; add default discriminator and optional base, then enforce branch checks and validate replacement FKs. Deploy compatible read/export first if needed and use an explicit feature gate for new writes. Backfill by default or a narrowly reviewed migration without rewriting provenance values. Baseline and populated upgrade, dump/restore under restricted search path, rerun, and mixed-version writer behavior require isolated PostgreSQL verification. Old API projections explicitly list legacy fields and only UPDATE rows. New endpoint returns both. Test old ORM rollback against migrated schema before enabling CREATE. Once CREATE exists, keep the expanded schema on application rollback and disable new writes. Restoring NOT NULL or deleting CREATE evidence is not an acceptable rollback.

For duplicate control, serialize CREATE by supplier using the existing lock order. Use the exact normalized key (brandId, manufacturerName, originalPartNumber, modificationEvidence, modification), scoped to the supplier. Check exact current identities under that lock across all active offers and recheck after locking. This guarantees contention between staged CREATE commands, and detects prior R1-007 manual writes. It does not impose a new uniqueness rule on later legacy manual writes. Any global constraint on legacy offers would require separate owner authorization and a duplicate remediation plan.

## Reconciliation persistence

Use append-only submission and confirmation tables. Submission keys include id, rowId, rowVersion, sourceId, sourceVersion, sourceHash, decisionId, supplierId, intended operation, nullable UPDATE offer/revision tuple, exact identity, bounded evidence and canonical evidence digest, author and time. Confirmation stores submissionId, same digest, confirmer, reason and timestamp, with UNIQUE(submission_id), UNIQUE(id,row_id,operation) as the application FK target and a composite FK to the submission key UNIQUE(id, digest). Add a composite reference from application (confirmationId, rowId, operation) to confirmation with the matching row and operation copied and validated against submission. Restrict UPDATE/DELETE and verify distinct employees and all root relationships under locks. Use CHECKs to require an UPDATE target and forbid one on CREATE. Apply revalidates the bound revisions and digest under its own locks. Confirmation conflicts and retries use the existing command receipt policy.

An active legacy offer that shares the exact manufacturer and part number, or the exact supplier part number, but lacks a complete variant or brand or has contradictory identifying facts, blocks CREATE as NEEDS_REVIEW. Only an archived exact match may be acknowledged as a warning. Candidate ranking does not remove a duplicate block.
