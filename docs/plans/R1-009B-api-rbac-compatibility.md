# R1-009B API and RBAC proposal

**DRAFT / REVIEW_REQUIRED / NOT FROZEN**

Under `/v1/staff/ingestion/rows/{rowId}`, using 64-character lowercase SHA-shaped row ID and UUID resource IDs. Strict bodies reject unknown fields. Versions are positive integers. Opaque preview tokens are server-issued, short-lived and bound to actor/session, operation, row version/hash, source version, decision, target, plan digest, reconciliation and duplicate warning set. Issue after authorized coherent reads. A token never grants access. Confirmation must reproduce the exact preview plan. For a committed receipt, check the current session and actor permissions, then fingerprint equality before token expiry or original session checks. The same actor may replay from a new valid session. Fresh execution requires the original preview session and unexpired token.

| Route                                       | Request                                                                                                                                                     | Response                                                                      |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| GET /review-inspection                      | none                                                                                                                                                        | 200 bounded PENDING row evidence and decision eligibility; no execution token |

Preview includes eligible, blockedReason, normalized exact identity, evidence status, field diffs and before/after freshness, bounded duplicate results and acknowledgement IDs. When warnings cannot be fully represented within bounds it blocks. Identity fields are brandId, manufacturerName, originalPartNumber, modificationEvidence and modification. Evidence items carry enumerated kind, restricted reference, exact supported fields and a bounded note. Confirmation binds frozen evidence and target. Receipt contains applicationId, operation, offerId, revisionId, version, rowId, runId, sourceId, sourceHash, decisionId, actorId, createdAt, optional reconciliationId and null baseRevisionId only for CREATE. Preserve required legacy audit semantics alongside the new provenance record.

Read baseline requires ingestion.read, suppliers.read, suppliers.offers.read. All POSTs use staff-bound CSRF and validated Origin. Execution additionally requires ingestion.review and suppliers.offers.write plus distinct proposed permissions ingestion.createOffer or ingestion.applyEdits. Reconciliation submission requires ingestion.review and proposed ingestion.reconcile. Confirmation additionally requires proposed ingestion.reconcile.confirm and a distinct employee. Previews require the corresponding execution entitlements. Registry additions default deny, with no grant to existing roles. Current authorization is checked before lookup and before any receipt replay.

Use existing actor-scoped ingestion command receipts. A mutating command supplies Idempotency-Key and canonical operation, row, actor, payload and preview identity form the request fingerprint. Lock receipt key, validate current permissions, load receipt, and return saved status/body for identical fingerprint. Changing payload with the same key returns IDEMPOTENCY_KEY_REUSED. Fresh command validates preview and locks source → supplier → target offer where present → row, preserving existing ordering. Recheck current versions and all invariants, write revision/root, domain audit, provenance and receipt atomically. Failed audit rolls back the mutation. Deterministic domain conflicts may be stored without business changes. Lost COMMIT response returns the saved receipt after retry with the identical key and content. Cross-target identities fail authorization or state validation without exposing data to unauthorized callers. A fresh intent after conflict needs a fresh preview and key.

R1-009A retains its existing DTOs, routes, exact identity rules, projections and idempotency behavior. Existing `/preview`, `/apply` and `/applications` contract stay stable. Use explicit legacy serializers for preview, applications and apply receipts. For consumed CREATE rows the legacy preview returns ALREADY_APPLIED with application:null. Legacy applications excludes CREATE records. All writers share global row uniqueness. Inspect exact status/response compatibility after migration. FROZEN R1-007 DTOs, permissions, supplier audit and public DTOs remain intact.

The preview digest binds all revision-affecting choices and the canonical sorted CLEAR field set. The execution fingerprint additionally binds the confirmation reason. Conflicts are replayed only after current authorization and identical fingerprint verification.

Use a versioned server-signed token with proposed 10-minute lifetime and rotation support. Its claims contain only IDs, versions and digests. Limit evidence to 1–5 entries, reference to 512 characters and reason/note to 500 characters. UPDATE reconciliation requires the target tuple, while CREATE forbids it.
