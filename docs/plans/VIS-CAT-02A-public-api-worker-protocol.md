# VIS-CAT-02A — Proposed Public API, Same-Origin Delivery, and Worker Protocol

**Status: DRAFT / REVIEW_REQUIRED / NOT FROZEN**

This is a future API contract proposal. Nothing described here is implemented or enabled by this document.

## Same-origin route selected for design

The current `infra/compose` and `apps/web` source has no configured Nginx/Caddy/Traefik/reverse-proxy rule for public catalog image bytes. The web container receives server-side `API_INTERNAL_URL`; it must never be copied to a client bundle. OD-MEDIA-09 selects one fixed same-origin Next.js Route Handler for the current design, forwarding only to one fixed NestJS media route. NestJS remains the authority for whether the exact product/revision/media is published. Production topology still requires a read-only deployment check before implementation; the repository source is not evidence of the deployed proxy topology.

Candidate browser URL:

`GET|HEAD /media/catalog/products/{slug}/{publicAssetId}/{renditionSetId}/{variant}`

Both HTTP layers enforce the canonical slug, reviewed path-safe ID grammars, fixed variants and GET/HEAD. Reject traversal, encoded separators, double-encoding, control bytes, extra segments, query parameters and request bodies. Test the actual proxy/router normalization chain so a malformed target cannot become an authorized route. Forward to one server-configured NestJS origin and fixed path with redirect following disabled. No caller value selects a host or URL. OD-MEDIA-10 defines identifier semantics. Encoding remains open.

Candidate backend route, pending versioned OpenAPI review: `/v2/public/catalog/products/{slug}/media/{publicAssetId}/{renditionSetId}/{variant}`. The new route and V2 product DTO are proposals; the existing frozen V1 public product routes and response schemas remain unchanged.

The Next fetch uses `cache: 'no-store'` and manual redirect handling; the Route Handler is not statically cached and forwards only the API's declared browser cache headers. It forwards only `If-None-Match`; it does not forward cookies, authorization, arbitrary headers, or client origin into the internal API. It does not reveal upstream host, internal URL, stack, or response text. It relays only the allowlisted headers `Content-Type`, `Content-Length`, `ETag`, `Cache-Control`, and `X-Content-Type-Options` on success/304. A `200` must have `Content-Type: image/webp`, `X-Content-Type-Options: nosniff`, a valid strong ETag, and numeric `Content-Length` within the approved profile cap for the requested variant; reject missing, invalid, or excessive values before sending headers. Count streamed bytes too; if they exceed the cap, stop upstream and abort downstream. Apply finite total and idle timeouts from the approved runtime profile. A timeout before headers aborts upstream and returns sanitized no-store `503`; a timeout after streaming starts aborts both streams and records a bounded availability result. Link the upstream AbortController to the downstream request signal so a disconnected browser cancels the internal request immediately. Status mapping is fixed: upstream `200` and `304` pass through; `404` becomes an empty no-store 404; `503` remains sanitized no-store 503; every other status, redirect, or invalid/over-limit response becomes sanitized no-store 503. HEAD never emits a body. Invalid local paths return 404 and disallowed methods return `405` with `Allow: GET, HEAD`. The handler does not cache independently of the API policy.

The NestJS route is the authorization point and can also be called behind a future verified same-origin proxy. It must not trust the Next handler as proof that media is public.

No endpoint accepts a FileVersion ID, FileObject ID, storage key, absolute URL, path, arbitrary variant dimensions, or a “public” boolean. Source and evidence references are never proxied as URLs.

Before reading or writing source bytes, reserve the unique actor-scoped idempotency key, target product, canonical metadata and exact server-owned storage intent. The full request fingerprint and source SHA-256 are computed from the completed bounded stream and recorded with the finalized reservation. In-flight duplicates return a bounded in-progress result and cannot start another writer. A completed replay verifies the same target, metadata and source digest before returning the original result; a different fingerprint conflicts. Processing retries bind to the exact job, attempt, source digest, profile and policy. Exact duplicate completion is a no-op. Reject stale or conflicting output. Upload and processing do not attach ProductMedia or publish a product.

## Public-byte authorization predicate and PostgreSQL boundary

For every GET, HEAD, and conditional 304, NestJS resolves the following predicates from one consistent MVCC snapshot. The future public read takes no `FOR UPDATE` or `FOR SHARE` row locks. Use one joined read statement; if an implementation needs more than one read, use a short read-only repeatable snapshot and close it immediately after authorization metadata is captured. Do not keep a transaction, snapshot, or row lock open while opening, hashing, spooling, or transferring file bytes.

The authorization snapshot is the request's linearization point. If a publish/unpublish/archive/revoke transaction commits before the snapshot is acquired, the read denies. If the read snapshot is acquired first, that already-authorized in-flight request may finish even if a later revoke commits while bytes are being verified or sent. This is the explicit boundary; revocation prevents later origin authorization, but cannot recall in-flight or already cached bytes. Do not claim a response-delivery-time revocation guarantee that would require holding database locks through storage/network I/O.

State-changing transactions use the existing R1-004 product-root serialization (`catalog_product ... FOR UPDATE`) first, then lock only the affected exact revision and media state rows in a stable order. Publish, archive, pointer change, media revoke, and the corresponding availability state/audit update must commit atomically. No filesystem or network operation occurs while these locks are held. The current product service demonstrates root-row locks for mutations; it does not implement this future public media route. This proposal adds no runtime locking behavior.

1. Strict slug resolves to an active, non-archived product; its `publishedRevisionId` is non-null and points to a `PUBLISHED` exact revision. Product/root identity and revision identity remain consistent. Category and brand satisfy current R1-004 public-active rules.
2. The exact revision has a `ProductMedia` relation whose ingestion target product, source FileVersion, stable asset ID, rendition set, and requested variant all match the path. No relation to a draft, pending-only, superseded, archived, or old set qualifies.
3. Ingestion is not revoked and has an eligible ready/available state; source digest matches the recorded immutable source; the source FileVersion is in `CATALOG_MEDIA_SOURCE` and its FileObject remains `PRIVATE`/eligible; the exact rendition set is READY and `VERIFIED_MEDIA_POLICY`; the selected profile's exact variant inventory was verified; the requested derivative FileVersion is in the derivative namespace, its FileObject is still `PRIVATE` and eligible, and its byte count/digest still match.
4. Rights attestation and evidence requirements are satisfied; product-match identity hash equals the server recomputation for that exact published revision; and `productMatchRenditionSetId` plus `productMatchManifestSha256` equal the exact displayed/current set. No source/set/manifest/rights/revision change invalidated confirmation.

The same snapshot must return only the server-owned immutable storage locator, expected length/digest, and fixed content type needed for this exact rendition. It must not resolve a caller-supplied path, FileVersion identifier, or URL. A missing row from an unpublished/invalid state is not distinguishable to the caller; storage failure after an eligible snapshot is a dependency/integrity `503`.

Unknown, malformed, unpublished, archived, revoked, stale-generation, or unauthorized media returns one indistinguishable safe `404` without exposing which check failed. A record already marked `UNAVAILABLE`, storage or database outage, timeout, missing referenced bytes, or checksum failure returns sanitized `503`, not a false product/media-not-found response. A public-request integrity failure may be recorded in sanitized operational telemetry; emit a `SYSTEM` audit action only when it is tied to the exact persisted job/attempt allowed by the R1-002 registry. Never fall back to an original, another generation, a guessed filename, or an external origin.

## HTTP and cache contract proposal

- Methods: GET and HEAD only. HEAD has identical authorization/status/headers and no body.
- Candidate success headers after a future cache-policy decision: `Content-Type: image/webp`, exact bounded `Content-Length`, `X-Content-Type-Options: nosniff`, strong quoted ETag containing the exact lowercase derivative SHA-256, and `Cache-Control: public, max-age=300, must-revalidate` as one experiment point only. The five-minute TTL is not approved or final; no cache header value is frozen before benchmark and owner review. No arbitrary `Content-Disposition`; no ranges unless a later reviewed requirement proves they are needed.
- To preserve a truthful pre-header 503 on corruption, this draft retains full-byte digest/length verification for GET, HEAD, and conditional 304, but performs it only after the short authorization snapshot has committed. Open the exact private object once through the server-owned storage root, reject symlinks/non-regular files, hash and count the full bounded bytes outside any DB transaction, then rewind and send from that same still-open immutable file descriptor. Do not reopen a pathname after verification. HEAD discards the body; 304 is returned only after authorization and full verification. If the storage object cannot be proven immutable while open, use a bounded private spool or fail closed. If storage fails after headers/body begin, abort the connection and record a sanitized integrity/availability event; never attempt a second response or substitute another image.
- Per-request hashing is a performance risk, not a measured guarantee: a page requesting 50–200 image variants can cause 50–200 full-byte scans before response. Keep it outside PostgreSQL locks, measure cold/warm storage and API/Next overhead under the benchmark plan, and compare against the explicitly unapproved alternative of verifying before READY plus a bounded integrity scrub. Do not remove per-read verification or select final caps/cache TTL without owner review of the security and benchmark evidence.
- `404`: same safe response for invalid/stale/unpublished/revoked media. `503`: dependency, byte integrity, or availability failure. Never return internal error strings or storage metadata.
- The roadmap records cache measurements and the required owner decision. Origin authorization is evaluated per request. Cache copies and in-flight responses have the revocation boundary described above.

## Public DTO proposal

The proposed V2 card response is `primaryImage: null | { publicAssetId, renditionSetId, altText, width, height, aspectRatio, variants }`; detail response is an ordered `images[]` with the same safe fields. `variants` is a fixed server-generated object of same-origin root-relative paths and fixed sizes/`image/webp`. Both identifiers are opaque locators, not capabilities; the NestJS route rechecks publication every time it reaches origin. Existing V1 responses receive no fields.

Do not expose FileObject/FileVersion IDs, namespace, storage key, original filename, upload staff, rights/source/evidence, internal state, audit, worker versions, or API origin. For catalog cards, use the fixed `THUMBNAIL`/`CARD` variants; for product details use the fixed `CARD`/`MAIN`/`LARGE` variants. A native `<picture>` with explicit same-origin `srcSet` and a measured responsive `sizes` value chooses the appropriate immutable URL without the Next optimizer's separate cache. If a Next component is used, it must preserve explicit same-origin variant selection and must not create another image proxy/cache. Width/height and accurate alt text prevent layout shift and preserve accessibility.

The first public gallery is a static ordered list of images, not a link, lightbox, carousel, or dialog. Do not add interaction or focus management in the initial public-media slice; any future viewer requires a separate keyboard/focus acceptance.

## Worker request/response protocol proposal

Two transports remain candidates. The bounded proof can reuse the VIS-CAT-02B `network=none` process with API-mediated streams through an isolated runner. A connected profile would require fixed API-initiated HTTP, no published worker port, proved API-only ingress and denied worker egress at the host/runtime layer. Neither profile gives NestJS Docker daemon access, the worker database/storage credentials, reusable secrets or caller-selected endpoints. Accept a result only on the API-initiated channel for the exact attempt. A nonce correlates the attempt and prevents replay. It does not establish peer identity or network isolation.

Request metadata is limited to: opaque `jobId`, `attemptNo`, source SHA-256, source byte count, detected input format, allowed profile version, allowed media-policy version, strict pixel/frame/byte budget, and a single-use random correlation nonce. Source bytes follow as a stream. Do not send FileVersion IDs, storage keys, paths, actor/session information, rights/source metadata, reusable credentials, API origin, or public IDs. The worker echoes the nonce and exact job/attempt/source/profile/policy tuple in its response; the API atomically consumes the nonce bound to the active attempt and rejects missing, expired, replayed, or mismatched responses.

Worker returns a bounded manifest plus exactly the required variants; each variant includes fixed enum, actual width/height, byte count, SHA-256 and WebP bytes. The API independently hashes/counts and writes the response to bounded private staging. It then passes those exact staged bytes to a verifier that independently decodes every output, measures dimensions/pixel/frame count, checks metadata stripping and variant completeness, and returns a bounded result bound to the job, attempt, digest and profile. Only after the API validates that result does it promote immutable bytes and, in a short fenced transaction, record FileVersions, rendition rows, verified set state and audit. The privileged API never passes untrusted output to an in-process full image decoder.

### Why the verifier is a separate trust boundary

The owner selected independent output verification in OD-MEDIA-07. A worker response, signature, or manifest cannot prove that compromised decoder/re-encoder code emitted only the allowed WebP profile. The verifier parses worker-produced bytes, which remain attacker-influenced, so it also needs a constrained decoder environment.

| Candidate boundary                                                           | Security result                                                                                                                                                                                                                                                             | Operational cost / disposition                                                                                                                                                                  |
| ---------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| One worker process both decodes/re-encodes and declares its own output valid | No independent verification; a compromised worker controls bytes and attestation.                                                                                                                                                                                           | Rejected.                                                                                                                                                                                       |
| Separate worker and verifier OS processes in one container                   | Can be independent only if distinct non-root UIDs, ptrace/process isolation, read-only verifier executable/root, bounded IPC, strict syscall/resource limits and a proven network boundary are enforced. A shared network namespace and image filesystem make proof harder. | Lowest service count, but not assumed sufficient; AppSec must accept the exact host/runtime controls before freeze.                                                                             |
| Separate worker and verifier containers; API mediates each bounded stream    | Clearer process, filesystem and network-namespace separation. Worker cannot invoke verifier directly; API alone sends the exact staged output to the verifier and accepts a result bound to job/attempt/digest/profile. Both receive no DB/storage credentials.             | Proposed minimum for the current security basis. Adds a second image/process to patch/observe, a bounded byte handoff, and decoder CPU/RAM; process sequentially to avoid overlapping peak RSS. |

The reference for the next proof is a separate non-root verifier container with its own network namespace and executable boundary. The API mediates the bounded stream, and the worker has no authority over the verifier or its result. AppSec must decide whether a different decoder implementation is required. VIS-CAT-02B exercised separate containers using the same codec build.

This boundary costs a second decoder execution, a bounded output handoff, another image/process to patch and observe, and separate memory/CPU limits. Run the worker and verifier sequentially for an attempt to avoid overlapping peak RSS. A verifier inside the same worker process or an API in-process decode is not independent and is rejected.

Suggested internal errors are finite codes such as `UNSUPPORTED_INPUT`, `DECODE_REJECTED`, `LIMIT_EXCEEDED`, `PROCESSING_TIMEOUT`, `WORKER_UNAVAILABLE`, `OUTPUT_INVALID`, and `STALE_ATTEMPT`. Do not return codec exceptions or input contents. Timeouts/crashes remain retryable where safe; source bytes stay private. No worker-originated READY, publish, audit-as-staff, or storage operation is accepted.

## Caller-visible safe errors and rate limits

Use existing API conventions; proposed errors distinguish unauthorized staff (`401`/`403`), invalid business state or stale version (`409`), source/profile validation (`422`), upload too large (`413`), rate/size quota (`429`), and dependency outage (`503`). Do not translate API outages into “image not found.” Public path failures remain uniform 404 as above.

Before freeze, define measured caps for concurrent uploads per actor, concurrent jobs per actor/product, queued attempts, per-product retained bytes, aggregate source+rendition bytes, global staging bytes, active verifier/worker count, and anonymous public reads. Reject new work before storage reservation at a hard cap or disk watermark; alert before the hard threshold; never delete linked files to restore capacity. Numeric values remain benchmark candidates in the roadmap. No new production flag is enabled by this proposal; any future flag defaults off and cannot make `/request-quote` or unrelated public file routes indexable/downloadable.
