# R1-010D policy B: immutable storage and byte identity

**DRAFT / REVIEW_REQUIRED / NOT FROZEN — DESIGN_GATE_BLOCKED.** Applies to [trust model](R1-010D-verifier-trust-boundary.md) and proposed download protocol. Existing #28 `PrivateFileStorage.openInquiryQuarantine` opens `r`; scan-only handle hashes at EOF. DB immutable key/hash/size and one handle do not prevent in-place modification; bytes may already have left before an EOF hash failure. No immutable object/version or protected download snapshot has been demonstrated.

| Option                          | Property and gap                                                                                                                                      | Resource/decision                                                                                                          |
| ------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Content-addressed name only     | detects mismatch only if rehashed before use; name cannot prevent overwrite, hardlink or privileged writer                                            | alone insufficient                                                                                                         |
| Versioned immutable object      | pins object version if store actually enforces retention/write denial for all runtime principals; protects rename/recreate and concurrent reads       | requires proven versioning/permissions; no object store assumed                                                            |
| Protected snapshot              | complete copy, verified size/hash before headers; private temp namespace, separate snapshot owner and read-only consumers; exact sealed object served | up to one extra 50 MiB per in-flight snapshot plus source, bounded concurrency, disk I/O; no hardcoded production capacity |
| Pre-hash then reopen source     | cannot stop replacement/in-place modification between hash and read                                                                                   | insufficient alone                                                                                                         |
| CAS + immutable sealed snapshot | deterministic identity and verified bytes, protection by OS enforcement and separation, not key name                                                  | recommended if supported and tested                                                                                        |

Recommended: immutable versioned **sealed snapshot** on existing private local filesystem, without new storage service. A trusted storage sealing principal (separate from API, worker and intake writer; implementation location subject to owner review) creates a fresh private temporary regular file exclusively using safe directory handles, no path traversal/symlink following; rejects hardlinks/non-regular files, copies full bounded original, checks size/hash and fsync/atomic publish; moves into sealed namespace with unguessable version and write/delete/rename denied to all API/worker/intake/verifier and download readers. Sealing principal may write only new temporary files and cannot alter sealed objects once committed; if OS/ownership cannot enforce this against that principal, design is BLOCKED, require privileged sealer split or proven immutable versioned storage. Administrative/root/storage-owner compromise explicitly trusted. Do not publish partly written objects or reuse version/key. Record exact snapshot ID, original document/key/digest/size in DB; verifier scans the protected version and download opens that exact version; the immutable protection must hold through final byte/abort, not only until open. Prevent link traversal, rename/replace, unlink/recreate and mutable aliases using OS primitives and permission tests on target OS/filesystem; no universal portability claim.

Fallback: per-download preflight copy and hash into a separate sealed private snapshot, then stream _that same sealed snapshot_, not reopen source. A newly copied snapshot has a different object version; this fallback is BLOCKED until a separate owner-approved trusted attestation binds the scanned immutable object version to the new sealed snapshot version and verifies full digest/size before headers. Digest equality alone does not establish the required object binding. Source alteration between evidence and copy causes denial. This fallback still requires protected temporary object against writers during check and stream. Shared writable tmp or hash at end is not safe. Neither option relies on SHA collisions being impossible in a mathematical sense; SHA-256 collision resistance is a documented assumption. Preserving 10/50 MiB originals and historic audit is mandatory; historical files without proven provenance get no automatic evidence or eligibility and any new historical scan requires separate lifecycle approval.

Stream: before HTTP headers fully materialize and verify snapshot, obtain authorization commit, hold protected snapshot until close; an abort destroys handles and releases temporary resources safely, no original deletion. If disk/full/quota/permission/integrity failure before headers: fail closed, mapped 503 or generic 404 as contract; after headers abort connection and record sanitized best-effort abort when DB reachable, never promise response replacement. 10 MiB candidate CSV and 50 MiB upload objects need bounded copy/read IO and concurrency quotas; benchmark low disk/free space, corruption, concurrent download, crashes and cleanup using synthetic data only. Cleanup cannot remove an active snapshot; reference-count/lease recovery must be reviewed, not guessed. Snapshot transfer/network, filesystem hardlink controls, durable fsync semantics and sealed owner privileges are unproven on target deployment; fallback is not a permission to enable CLEAN.
