## Boundary and recommendation

Recommend B: one separate verifier process/container in the existing Compose deployment, reusing PostgreSQL and private storage, with a dedicated verifier ClamAV instance, with a separate non-root UID, filesystem namespace, LOGIN, secret mount and network access. This is a **proposal for a new process**, not evidence it exists or is sufficient. API and scan-worker cannot enter its process namespace, read its credentials or invoke its DB functions; Docker host/root/admin, deployment orchestrator, DB owner/superuser, storage snapshot administrator and scanner binary/signature provisioning operator are explicitly trusted. Secrets mounted only into verifier; no Docker socket, host PID, shared writable filesystem, shared UID, ptrace/capabilities or verifier connection pooling accessible to worker/API. Prove with actual UID/GID, namespace, volume, process, permission and network adversarial tests on target runtime; process separation alone is not proof. A compromised API cannot issue evidence, but can directly read any protected snapshots available to its identity and exfiltrate them outside the HTTP gate. Confidentiality and enforcement against arbitrary code in API are outside this design boundary; the gate protects normal routed downloads and rollback, not an API compromise. A separately trusted serving process would require a new owner decision; do not claim this protection without it. Owner must approve this concrete trust boundary and resource budget before freeze.

A API-process verifier shares API memory/secrets; API compromise forges evidence, so fails separate-compromise objective. C reuse worker shares its credentials and assertions; compromised worker can mint evidence, fails objective. B adds one process, credentials, lifecycle, CPU/RAM/I/O and monitoring, but no new database, queue or broker. Per-document independent full scan increases latency and traffic. A shared scanner is an alternative only if an independently verified filter prevents worker control commands and verifier has an independently protected authenticated endpoint; worker's ability to connect must not let it impersonate or reconfigure that endpoint. For a verifier-dedicated scanner, use a Unix-domain socket mounted only read-only into verifier, peer/socket/directory ownership validated and scanner config/reload controlled by privileged deployer, no worker write, route or bind-mount control. A read-only mount alone does not authenticate a socket; prove socket endpoint and inode/owner through protected parent namespace, peer credentials where supported, and no replacement. The separate independently provisioned clamd instance is the recommended candidate and requires additional resources and owner architecture approval; a shared daemon with proven command filtering is only an alternative. Docker network alone is not endpoint authentication; TCP without authenticated protection is blocked. Shared-daemon DoS is fail-closed. Neither scanner endpoint nor storage server may accept arbitrary path or privileged control requests from worker.

## Data flow and measured evidence

Worker claims bounded job as today, but cannot issue a positive verifier assertion. Verifier obtains job/source/lease binding through narrow DB read function using its own LOGIN; it independently opens the protected immutable object identity and reads all original bytes, validates exact EOF, size, SHA-256 and selected policy-bound CSV grammar, sends the identical complete byte sequence via authenticated scanner connection, parses one complete protocol response and checks deadline. It obtains engine VERSION immediately before/after on the same verified daemon session; checks nonfuture signature metadata and ≤24h current age, pinned deployment image digest, stable epoch/reload generation with independently controlled reload serialization. A deployment-controlled signature bundle hash and scanner startup/load attestation must link the actual loaded database to that epoch; absent a reliable way to establish loaded content/continuity, **DESIGN_GATE_BLOCKED**, not an assumption. The current VERSION fingerprint hashes a metadata tuple; it does not hash loaded signature files, prove endpoint identity or detect all reloads. Same-handle EOF/hash and scanner `stream: OK` cannot prove internal scanner coverage or malware absence. Internal coverage, MaxScanTime and signature provenance remain NOT_PROVEN. Require real-pinned-scanner adversarial fixtures; no mock substitutes for them.

Verifier inserts append-only evidence and calls a verifier-only SECURITY DEFINER positive-finalize-and-issue function, not client `isComplete` or raw worker verdict. In the same transaction the function locks the job/source and policy/eligibility anchors, validates persisted evidence, authenticated issuer, matching lease/version and policy, then atomically finalizes, issues the unique slot and audit. Worker cannot call either function. This authority makes the verifier trusted; its compromise remains outside the protection guarantee. Fields: document/storage object version/key/digest/size, complete byte count/EOF, job id/version/token hash or verifier-bound lease reference, policy id/version/profile id, validator revision and result, scanner image digest/engine/signature metadata/bundle epoch and attestation references, start/end/expiry, issuer DB session identity and safe audit correlation. No capability, raw token, file content, credentials or signature response in audit. DB checks session_user against allowlisted LOGIN, membership, persisted bindings, expiry and transition; it cannot read bytes or verify scanner internals. Exact replay is no-write only for identical principal/version/lease and canonical fingerprint; conflicting replay/stale lease rejects. Issuer possession is powerful: compromised verifier can lie, so verifier itself is trusted and separately assessed, with compromise containment and credential revocation; no promise against it.

## Credential lifecycle and resources

Provision unique least-privilege LOGIN secrets out of Git using deployment secret store, mount only recipient, deny worker/API access, test permission and `/proc` exposure; no values in logs. Rotation creates replacement LOGIN, updates allowlist under owner-controlled procedure, tests fresh login and disables old LOGIN/terminates existing sessions; audit safe principal/version. Ordinary rotation of an uncompromised credential does not automatically invalidate historical evidence or eligibility. Suspected compromise triggers a separate audited transaction under the same policy/document anchors to revoke affected evidence/eligibility and block issuance, according to a separately approved incident policy; disable/rotate without assuming secret erasure. At most one active verification per initial deployment candidate, same fixed 180 s worker/240 s lease only if end-to-end benchmarks prove feasibility. Verifier validator candidate 1 CPU/256 MiB/zero scratch is not a container capacity guarantee; scanner has separate measured allocation. No production resource availability claimed.

## Scanner command boundary — security finding

The existing worker-facing clamd protocol must be treated as capable of administrative `RELOAD` / `SHUTDOWN` as well as scan commands: an attacker with that connection can disrupt or change the shared daemon. A verifier-only UDS does not prevent control over the same daemon through its worker TCP endpoint. **DESIGN_GATE_BLOCKED:** recommend a verifier-dedicated clamd instance with protected endpoint and signature lifecycle, isolated from the worker, subject to explicit owner architecture/resource approval. A single shared clamd is an alternative only if an independently verified command-filtering boundary denies all worker control commands, protects both endpoints and scanner configuration, and serializes/reliably attests signature reload throughout scanning; this extra gateway is not assumed to exist and would require separate design review. DoS is fail closed. The extra scanner can substantially increase RAM and CPU: measure it and obtain owner approval, do not assume existing VDS capacity.
