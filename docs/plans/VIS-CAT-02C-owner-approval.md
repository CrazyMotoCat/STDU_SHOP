## Предполагаемый том и пределы доказательств

Предлагаемый первый целевой профиль — **локальный ext4 на отдельном виртуальном блочном устройстве в Linux VM**, Docker local volume без remote driver поверх этого ext4. Staging и final находятся в одном файловом устройстве. Предполагаемые mount options — `rw,relatime,data=ordered` с включёнными барьерами записи, без `nobarrier`. Размер выделенного экспериментального устройства — 4 GiB, без общих данных. Это кандидат для испытаний, а не установленная конфигурация VDS.

Перед запуском владелец указывает тестовый хост и утверждает соответствие профиля предполагаемому VDS. На тестовом хосте зафиксировать `findmnt -T`, `stat -f`, `stat -c %d` для staging/final, `lsblk -f`, версии ядра/Docker, тип диска, Docker volume driver/options и разрешённый read-only вывод mountinfo из контейнера. Отдельно сравнить тот же перечень с предоставленным владельцем описанием целевого VDS. Совпадение только имени ext4 недостаточно. Зафиксировать слой виртуализации, параметры виртуального диска, режим кэша и доступные гарантии flush. Если целевой профиль не установлен либо отличается, E1–E5 могут дать только лабораторный PASS. Соответствие VDS остаётся NOT_PROVEN.

Создание/форматирование устройства, настройка Docker daemon, firewall и перезапуск VM требуют отдельного задания на отдельном тестовом хосте. Этот план не содержит разрешения выполнять их на рабочем компьютере или VDS. Допустимый старт после утверждения — проверка уже подготовленного пустого экспериментального устройства. Если такого устройства нет, испытания тома BLOCKED. tmpfs и Docker Desktop overlay не подменяют ext4 в протоколе.

## Изоляция и предварительный gate

Каждый запуск имеет случайный UUID. Контейнеры, сети и тома создаются заново с точными именами и label владельца `stdu.vis-cat-02c.run=<UUID>`. Подключение существующего тома или сети запрещено. Harness проверяет, что имена отсутствовали до создания, и сохраняет полученные ID. После PASS E0a на созданном media-томе создаётся случайный sentinel. Для PostgreSQL используется другой новый том, другой sentinel и база `vis_cat_02c_<UUID>` с отдельными случайными credentials, передаваемыми только контроллеру и PostgreSQL.

Контроллер использует положительный allowlist ID всех ресурсов и точную таблицу разрешённых mounts. Docker inspect проверяет source каждого mount, имя сети, отсутствие host networking, Docker socket, privileged, host PID/IPC namespace, дополнительных bind mounts и опубликованных портов. После PASS E0a контроллер создаёт одноразовую базу и sentinel. В E0b он проверяет имя базы, sentinel и отсутствие прикладных таблиц STDU_SHOP до запуска workload. Миграции приложения не используются. Доступные runtime-credentials не позволяют создавать базы или роли. Временная схема intent отделена от Prisma и FROZEN моделей.

OPS-TEST-02 исключён из allowlist по ID и namespace. Ни его ресурсы, ни родительские каталоги не могут быть mount source. Обнаружение общего ресурса, неоднозначного владельца или неизвестного Docker context останавливает запуск до инициализации SQL и файловых записей. E0a проверяет создание и принадлежность новых ресурсов по metadata. Только после PASS E0a разрешены контролируемая инициализация базы и запись sentinel в проверенные owned volumes. PASS E0b подтверждает их идентичность перед workload. Изоляция гарантируется только после успешного preflight на конкретном стенде и проверки этих фактов независимым reviewer. Совместный Docker daemon сам по себе не является границей доверия против его администратора.

Worker/verifier работают с разными непривилегированными UID, read-only root, dropped capabilities, no-new-privileges и без секретов БД или доступа к media/PG томам. Для первой лабораторной серии обмен идёт через stdin/stdout под контролем harness, а оба контейнера имеют `network=none`. Подключённая API-only топология рассматривается отдельным экспериментом E4b и допускается только после утверждения правил host/runtime egress.

## Общие бюджеты и остановка

Значения ниже предлагаются для утверждения. Фиксируются pinned image digests и синтетический manifest из 02B. Один decode job использует прежние 8 MiB input, 5 миллионов pixels, 2 MiB на вариант и четыре варианта. Полный набор кодеков повторно не запускается без проверяемой гипотезы.

| Ресурс                          | Предлагаемый предел                                                                                                                                        |
| ------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Worker или verifier             | 1 CPU, 256 MiB RAM, memory-swap равен memory, 32 PID, 32 MiB tmpfs                                                                                         |
| Controller                      | 1 CPU, 256 MiB RAM, 64 PID                                                                                                                                 |
| PostgreSQL                      | 1 CPU, 512 MiB RAM, 64 PID, максимум 10 connections                                                                                                        |
| Canary-контейнеры суммарно      | 1 CPU, 128 MiB RAM, 32 PID                                                                                                                                 |
| Последовательность одной работы | Worker и verifier последовательно, максимум два контейнера обработки одновременно при двух jobs                                                            |
| Весь стенд для concurrency 1/2  | Не более 5 CPU квоты и 1.5 GiB RAM квоты суммарно, включая инфраструктуру                                                                                  |
| Storage                         | Выделенный ext4 4 GiB, до 256 MiB media, до 512 MiB PG, до 128 MiB журналов. Проверка свободного места перед каждой попыткой, stop при остатке менее 1 GiB |
| Время                           | Create/start workload вместе до 30 секунд, cleanup до 10 секунд по общей monotonic deadline                                                                |
| DB barriers                     | До 10 секунд на ожидание барьера, statement/lock timeout до 5 секунд, транзакция до 15 секунд                                                              |

Вариант concurrency 4 из исходного плана остаётся отложенным до отдельного решения по данным concurrency 1/2 и бюджету хоста. Сначала обеспечить внешний общий watchdog на стенде, резервирование диска до записи и ограниченный размер журналов. При OOM, неподтверждённой остановке, первом нарушении инварианта или исчерпании лимита остановить серию и сохранить evidence. Исходы FAIL и BLOCKED не превращаются в PASS по успешному retry.

Для E3b missing/corrupted fixture вносится намеренно и помечается как external fault. Требование «нет ссылок на недоступные bytes» относится к ссылкам, создаваемым workflow. При уже внесённой внешней порче PASS означает обнаружение, отказ в признании валидности, сохранение истории и безопасную диагностику. Восстановление содержимого из резервной копии этим тестом не доказывается.

Expiry оценивается по времени БД под блокировкой в точке решения. Delay перед COMMIT проверяется отдельным барьером. Заявлять гарантию expiry на момент фактической фиксации допустимо только после отдельного выбора семантики и её доказательства. Это открытый вопрос решения C-03.

## C0 — очистка и сохранение evidence

Контроллер записывает точные resource IDs и уникальный owner label до запуска участников. При прерывании create неизвестный исход обрабатывается как в 02B-FIX. Совпадение имени без owner label не даёт права удаления. При shutdown подтверждаются остановка и отсутствие контейнера через inspect, команды делят cleanup deadline 10 секунд. Если daemon недоступен либо принадлежность/остановка не подтверждены, выдаётся CLEANUP_UNCONFIRMED с именами/IDs, новые работы прекращаются, volumes и evidence сохраняются для ручного расследования.

После подтверждённого завершения писателей сохранить JSON и hash manifest на хосте по отдельному каталогу текущего run. Перед удалением ресурсов повторно сравнить IDs/labels с creation ledger и sentinel. Контейнеры удаляются по ID, сети по ID, тома — только по точным names/labels нового run, после отдельной проверки отсутствия подключённых контейнеров. Автоматического удаления orphan-томов по префиксу, prune, `down -v` и удаления host paths нет. Экспериментальный диск и его разделы остаются на стенде до отдельной процедуры вывода из эксплуатации. Право удалить именно временные volumes утверждается в C-05 до запуска. При отказе cleanup том сохраняется с явной записью residual resource.

## Разделение разрешений

Безопасная лабораторная часть после отдельного одобрения C-01…06 — E0, E1, E2, E3, E3b, E4a и E5 на подготовленном тестовом хосте и новых ресурсах. Кодек ограничен синтетическими fixtures.

Действия с повышенным воздействием — подготовка/форматирование диска, смена firewall/daemon policy для E4b, реальные ENOSPC на файловой системе, перезапуск или отключение питания хоста. Они требуют отдельных точных разрешений, отдельного стенда и гарантии отсутствия рабочих данных. Инъекция ENOSPC через mock не является испытанием поведения реальной файловой системы при полном диске. Production rollout и реальная media pipeline находятся за пределами плана.
