## PR #28 compatibility and safe integration order

Draft PR #28 adds scan jobs, worker finalization and private scan streaming. Its current FROZEN R1-010D references assume CLEAN-only download. This amendment changes only the caller-facing release policy: a worker may still finalize `CLEAN`, but that result must not reach a staff download path. The existing download service is not changed by PR #28's current changed-file set; PR #33 is the sole change to that service. The private scan stream remains an internal, lease-bound worker path, not a staff download path, and its authorization is unchanged.

Safe future order: (1) keep this contract PR dependent on the PR #33 branch so its combined candidate receives exact-head CI; (2) after a separate owner merge decision, integrate the contract commit into PR #33 and merge the combined candidate to main only after fresh checks; (3) rebase/synchronize PR #28 to the resulting main, verify the worker's CLEAN finalization does not reopen the staff download path and run fresh checks; only then request a separate merge decision for PR #28. PR #28 is not modified by this contract PR. No migration, production data operation, deployment or CLEAN enablement is authorized.

## OpenAPI/runtime compatibility

The FROZEN OpenAPI removes the successful binary response until a future exact-original eligibility amendment is approved and records `x-audit: none`. The Inquiry OpenAPI exporter copies response metadata from the frozen contract but reads `x-audit` from the NestJS `StaffOperation` decorator. PR #33 therefore changes only that route's decorator to `audit: 'none'`; the runtime method continues to deny before opening storage. Exact generated-operation response and audit-policy parity must pass on the combined PR #33 + contract candidate.

## Encoded static-route finding — separate follow-up

`GET .../documents/{documentId}/%64ownload` does not reach the download handler in the current Nest/Express route matching. The test confirms no storage open and no source bytes. It currently returns 500 `INTERNAL_ERROR`: `HttpBoundaryFilter` maps an unmatched staff `HttpException` as an unknown error, while its special 404 normalization is limited to public Inquiry routes. This is a shared routing/error-boundary behavior, so PR #33 keeps the existing observed result and records the no-bytes security property. Track `SEC-API-ROUTE-001` separately to review encoded static-path normalization and non-enumerating staff 404 mapping across all staff routes; do not broaden the L0 fix without its own regression matrix.
