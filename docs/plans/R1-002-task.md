# R1-002 — staff identity, permissions and foundational records

Шаблон следующего ограниченного задания. Его наличие не означает разрешения начать R1-002 до приёмки R1-001.

## Цель

Сотрудник входит в систему и выполняет только разрешённые сервером действия; неавторизованный или лишённый разрешения клиент получает отказ. Создать минимальные записи собственных продавцов, audit и file references для последующих задач.

## Источники и зависимости

- Принятый R1-001 и ADR-001…004; Node/pnpm/Python/uv версии и lock-файлы сохраняются.
- Backlog R1-002; ADM-01, ADM-03, инфраструктура QUOTE-03/REQ-04 без реализации КП/загрузок; решения 10, 16, 49, 50, 55, 85.
- Сессии сотрудников отдельно от будущих клиентских quotation links.

## Сначала зафиксировать контракт

Один ведущий владелец фиксирует таблицы/ограничения/индексы, API DTO и HTTP-коды, permission matrix, транзакции/audit, bootstrap первого сотрудника, session expiry/revocation и CSRF. Затем реализация в отдельной ветке. Если вопрос меняет бизнес-правило, вынести его владельцу; ролевые шаблоны не превращать в жёстко заданные права.

## Разрешённая область

- `apps/api`: StaffUser, Role, Permission, UserRole, RolePermission, StaffSession; минимальные SellerLegalEntity, AuditEvent, FileObject/FileVersion/FileLink references по согласованной схеме.
- Prisma client/adapter и первая versioned migration; одна точка применения миграций, отсутствие запуска из startup.
- Staff login/logout/me, серверная проверка session + permissions с default deny; хэш сессионного токена, Argon2id, сроки/отзыв, CSRF и login rate limits.
- Безопасный локальный bootstrap без пароля по умолчанию; конфигурация собственных юрлиц без выдуманных боевых реквизитов/налогов.
- OpenAPI и сгенерированный TS-клиент первого staff API; минимальный тестовый UI входа только если явно включён в контракт задачи.
- Тесты, fixtures, необходимые CI/README обновления и checkpoint.

## Приёмочные примеры

1. Миграция применяется к пустой БД и повторно запускается без повреждения данных; сценарий с заполненными fixtures сохраняет данные и ограничения.
2. Гость получает 401 на staff API; сотрудник без permission — 403; назначенное разрешение даёт доступ. Проверка выполняется NestJS.
3. Неверный пароль не раскрывает наличие пользователя; лимит входа проверяем; токены/пароли отсутствуют в ответах и логах.
4. Истёкшая или отозванная сессия, отключённый сотрудник и небезопасный запрос без CSRF отклоняются; logout отзывает сессию.
5. PostgreSQL хранит проверочный хэш session-токена, а не cookie-значение. Несколько ролей объединяют разрешения согласно зафиксированной матрице.
6. Собственные продавцы не смешиваются с клиентскими контрагентами; служебные audit/file refs недоступны гостю. Файловые ссылки ещё не дают публичного скачивания.

## Жёсткие исключения

Нет каталога, парсеров, upload/download API и сканера, заявок/калькуляций/КП, клиентских кабинетов, заказов, склада, производства, нового IdP, платных сервисов или автоматических бизнес-согласований. Не добавлять схему последующих модулей «на будущее».

## Обязательные доказательства

Корневые lint/format/typecheck/test/build, PostgreSQL migration tests на пустой и заполненной БД, реальные API/session/RBAC denial tests, применимые smoke и CI на точном SHA. Отчёт содержит пути, фактически выполненные команды, результаты, ограничения и следующий ограниченный шаг. Невыполненные проверки отмечаются NOT RUN с причиной.
