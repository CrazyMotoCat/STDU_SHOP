## Separate codec gate

Worker and verifier each have a project limit of 128 MiB, 0.75 CPU, 16 PID and an 8 MiB scratch budget, with zero extra swap. The four limits total 512 MiB. With PG and controller present and worker/verifier serialized, the configured active cap is 384 MiB. Neither is actual usage nor an OS reserve. E5A cannot establish codec headroom.

A future separate decision must fix the codec image digest, synthetic input and expected output hashes, and authorize any build, pull or WB workload explicitly. Proposed workload is one bounded decode and one verification sequentially, one controller slot, 30 s workload and 10 s cleanup per component under the same host floors, no mounts carrying real files, no networking or credentials. Apply the above measurement and block criteria. Keep both NOT_RUN until physically observed. No fault injection or power-loss test belongs to E5.

Owner gate for the next physical stage is OWNER_E5A_RUNTIME_APPROVED for one E5A campaign on a reviewed measurement-runner HEAD. This preparation supplies the runbook and offline acceptance checks.

The entry point is `e5a_run.py`. It requires the exact owner token, Linux root, the accepted daemon identity, a clean checkout and unchanged retained evidence. That token is a technical guard. A separate owner decision remains required before invocation. It runs `runtime_e5a.py` with the concrete `HostBackend`, which starts a separate process watchdog before either provisioning worker. Workload intents are exclusive, fsynced records. Each phase derives a separate resource identity from the campaign ID. Worker PID/start time is recorded before its start gate opens. No create is repeated after an ambiguous response.

The watchdog reads the protected journals itself, pins process identities, checks host and cgroup counters, and publishes its latest sample through a bounded fixed-size buffer. A runner that stops reading cannot block the watchdog. Lost heartbeat or runner exit terminates only an identity-verified provisioning worker before addressed resource cleanup. Cleanup is serialized with a run-local lock. A failure retains its first bounded code and a separate cleanup report. Unknown ownership, attachments and unknown socket remnants produce unconfirmed cleanup.

The SQL adapter uses the actual PGconn socket from libpq, reads Linux SO_PEERCRED, pins the socket FD/inode, and checks the expected server PID/start time. Docker attestation additionally pins that process to the exact container cgroup. The transactional marker binds the SQL session to the generated database and nonce. Local integration confirmed that the listening postmaster peer, rather than an assumed per-session backend PID, is reported for this Linux PostgreSQL build. Other namespace and platform behavior remains subject to physical verification. Authentication is constrained to the test profile's trust method and ambient PG configuration is refused.

The strict evidence validator accepts only its fixed envelope, phase results, typed counters and bounded arrays. It retains SQL outcomes, fsync durations, sampled PG/media bytes, Docker infrastructure RSS/CPU ticks, PID/start time, resource IDs and watchdog outcome. Each container sample must match the envelope's exact ID. Evidence publication uses a private temporary file, fsync, a no-replace link, directory fsync, readback and SHA-256. A PASS cannot be returned after an evidence write failure.

Offline checks are `python3 -B -m unittest discover -s experiments/wb-lab-01`. The concrete backend test uses fake Docker transport, actual separate worker/watchdog processes and the four-phase coordinator, then seals the resulting evidence. It includes an unresponsive reader, a late watchdog abort, SQL-phase crash recovery, resource substitution and foreign attachments. These tests do not exercise the physical WB or prove its filesystem, service headroom or collection latency.

For a separately provisioned, isolated Linux test environment with extracted PostgreSQL 18 binaries, `WB_E5A_REAL_PG=1 WB_E5A_PG_PACKAGES=<extracted-root> python3 -B -m unittest discover -s experiments/wb-lab-01 -p test_e5a_real_pg.py` runs the real integration. The extracted root must include libpq and its dependent libraries on the loader search path, plus libnss_wrapper for the synthetic UID 999. The test initializes a private temporary cluster, publishes no TCP listener and stops only its own process. It does not install a system service.

Real local PostgreSQL 18.6 measurements passed on 2026-11-15. Three transactions completed in 8,431 / 5,261 / 5,199 us including verification. The third committed acknowledgment was discarded and a fresh read-only session confirmed it without a repeated INSERT. The bounded row lock waited 1,000,843 us and statement timeout completed in 2,504 ms. A wrong process start time was denied and shutdown removed the private cluster's postmaster PID file. These amd64 WSL timings are not WB resource measurements.

The future physical profile still needs observed Docker API latency at the 250 ms sampling cadence, ARM64 bootstrap and cgroup validation, and measured service/resource headroom. The concrete profile fails closed if sampling cannot meet its existing freshness constraints. Filesystem apparent-size monitoring is independent of filesystem quota enforcement. RSS and cgroup usage are reported separately.

The paired SQL watchdog checks apparent file bytes every 250 ms within the supplied phase deadline. A sample at or above 128 MiB, an unavailable sample or an overdue sample blocks the phase and starts addressed cleanup. This is a sampled stop threshold. Writes can exceed it between samples and the filesystem does not enforce it as a quota.
