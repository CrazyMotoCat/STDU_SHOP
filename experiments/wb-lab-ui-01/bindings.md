# SVG bindings

## Compatibility

The SVG editor's JSON mode edits the dashboard's binding `params`. HomeUI 2.267.7 serializes the array with `JSON.stringify` and parses it with `JSON.parse`. JSON syntax and editor parse/serialize compatibility: PASS.

The first desktop canary exposed a renderer issue and was removed. After the binding and metadata fixes, both panels passed cold start and DEMO checks. The HomeUI export preserved the SVG bytes and all 35 binding entries for each panel. The original two panels remained unchanged.

## File and mapping

[`bindings.json`](bindings.json) is generated by [`generate_dashboard.py`](generate_dashboard.py). Each `id` exists, unchanged, in both `dashboard-desktop.svg` and `dashboard-mobile.svg`, so the same JSON array can be imported into either panel.

The renderer calls `read.value` as soon as a binding attaches. It then assigns the result to SVG `innerHTML`. Each expression supplies a neutral fallback for a missing or empty value. The text expressions escape markup and validate enumerated states. Numeric expressions distinguish zero from missing data and add a unit only after validating the payload. The `DEMO · SYNTHETIC` badge is unbound.

The `read.channel` and `style.channel` properties use HomeUI cell IDs such as `stdu_lab/Progress`. The corresponding broker topic is `/devices/stdu_lab/controls/Progress`.

The bindings use only:

- `read`: display a control value as text; progress and measurements append their documented units.
- `style`: map allowlisted status strings to fixed CSS fill colors. Status values are validated against the finite contract enum.

The JSON has no `write`, `click`, `long-press-write`, or dashboard navigation actions. There are no controls, buttons, or links in the SVG.

## HomeUI import readiness

This procedure applies to an owner-authorized stand import. The current installation used the installed HomeUI's per-dashboard API. Future imports require the exact owner instruction `OWNER_HOMEUI_IMPORT_APPROVED` or an equivalent scoped authorization.

### Pre-import backup and compatibility gate

Repeat the read-only checks immediately before each write through HomeUI. No direct edit to `/mnt/data/etc/wb-webui.conf` is allowed:

1. Confirm the installed HomeUI version and export every existing dashboard/panel artifact and its JSON bindings through the UI. Save the exports off-controller in a timestamped, access-controlled backup directory. Record dashboard IDs, names, file sizes, and SHA-256 hashes in a manifest; verify every exported file is readable before proceeding. Do not edit or replace any existing panel.
2. If an existing SVG panel is available, export its bindings from the target's own editor and compare the JSON shape with `bindings.json`. Require a JSON array of per-element objects. Validate every `id` against both supplied SVGs; IDs must be unique within each SVG and in the bindings array. The same stable SVG element IDs are intentionally shared by the two separate panels. If no existing SVG editor export is available without changing an existing panel, use the desktop panel as the first import canary after approval; do not create or edit a separate panel just to obtain a sample.
3. Check the dashboard inventory for panel IDs `stdu-lab-desktop` and `stdu-lab-mobile`. Never overwrite an existing ID. If either is already present, choose a new unique suffix and record the actual IDs in the manifest before adding anything.
4. Recheck the binding allowlist: only `read` and fixed `style` actions; all cell IDs under `stdu_lab/` and mapped only to `/devices/stdu_lab/controls/`; no `write`, `click`, `long-press-write`, navigation, or `/on` channel. Do not import if any check fails.
5. Check the exact allowlisted MQTT channels and the scoped namespace. On the verified Mosquitto 2.0.21 broker, require successful subscriptions and observe the trailing retained `$SYS/broker/version` replay marker in the same subscription request. An elapsed timeout is insufficient. If the marker is unavailable or any value appears before it, stop and do not clear or rewrite the entries. This prevents a retained `PASS`, `RUNNING`, or synthetic value from replacing the neutral SVG defaults on first load.

### Add and verify new panels

6. Add the desktop SVG as a **new** panel with its unique panel ID and HomeUI fit-to-page enabled. Apply `bindings.json` and verify neutral `UNKNOWN`, `NO_DATA`, `NOT_RUN`, and em-dash states while the namespace is empty. If the desktop canary fails, remove only its exact new ID and stop before adding mobile. Do not connect or configure a LIVE source.
7. Only after desktop passes, add the mobile SVG as another new panel with a different panel ID. Disable fit-to-page for mobile so that the installed HomeUI scrolls at the full available width. At 375–390 px, scroll to the events footer to verify it remains reachable. Verify the `DEMO · SYNTHETIC` marker remains visible and confirm the binding editor contains no command action.
8. Export both new panels and bindings again. Check their IDs, bindings, and SHA-256 against the manifest; confirm every pre-existing panel ID and backup checksum remains unchanged. Do not enable HMI mode or command bindings as part of this import readiness check.

### Addressed rollback

If either new panel fails validation, stop and remove only the exact new panel ID or IDs recorded in the manifest. Do not delete, replace, edit, or restore over pre-existing panels. If a pre-existing panel appears changed, stop the operation and leave it untouched; report the discrepancy for a separate owner decision. Verify the dashboard inventory afterward. Never edit the global config file directly, clear `/devices/#`, or delete MQTT topics as rollback.

The [official SVG Dashboard guide](https://wiki.wirenboard.com/wiki/SVG-Dashboards) documents unique panel IDs and the UI export/import flow for bindings JSON. The plan above adds per-panel backups, namespace checks, ID collision handling, and targeted rollback. The installed HomeUI API supports the same dashboard payload. On 2.267.7 a new random URL ID with the intended panel ID in the PUT body rejects an existing target atomically with HTTP 409. Require HTTP 201 for creation, then verify the final target ID and export.

## Expression note

The style expressions are ordinary JavaScript conditional expressions using HomeUI's documented `val` variable. The upstream renderer evaluates a binding expression against the selected MQTT value. The contract constrains every style input to known status enums; no log text or arbitrary value is returned as CSS.

The safety panel calls this value `SAMPLE AGE AT SEND`, with the fixed note `Age when published · OFFLINE = retained / last known`. `Telemetry_State=FRESH` renders as neutral-colored `FRESH AT SEND` and describes the age reported with the last published sample only. `Collector_Status` is displayed as a separate connection status. When the collector goes offline, the Last Will updates only the collector control; the broker can still return retained `FRESH`, `RUNNING`, or `PASS` values. These are last-reported values, not proof that a run is active or the collector is available. The HomeUI bindings cannot combine these channels into an effective freshness value.
